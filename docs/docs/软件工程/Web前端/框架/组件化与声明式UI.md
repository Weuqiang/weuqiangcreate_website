# 组件化与声明式 UI

## 学习目标

学完本章，你应该能够：

- 对比命令式与声明式两种 UI 编程范式
- 解释「组件」封装了什么
- 理解状态（state）驱动视图的思想
- 说清单向数据流解决的问题

## 前置知识

在阅读下面的内容前，建议先掌握：

## 核心概念

现代前端框架的共识是：**UI 是状态的函数**——`UI = f(state)`。你描述「界面长什么样」，框架负责把它变成、并保持成真实 DOM。这与早期「手动改 DOM」的命令式写法截然不同。

本章主线：

- 命令式 vs 声明式
- 组件：封装结构/样式/行为
- 状态驱动视图
- 单向数据流

## 命令式 vs 声明式

命令式（jQuery 时代）：

```javascript
// 手动找到节点、手动改
const count = document.getElementById('count');
count.textContent = String(n);
if (n > 10) count.classList.add('warn');
```

你要一步步告诉浏览器「怎么做」。状态一多，手动同步 DOM 与数据的代码迅速腐化。

声明式（框架时代）：

```jsx
function Counter({ n }) {
  return <div className={n > 10 ? 'warn' : ''}>{n}</div>;
}
```

你只描述「n 是多少时界面什么样」，框架在 `n` 变化时自动重渲染。关注点从「步骤」转向「结果」。

## 组件：封装三件套

组件把**结构（HTML）、样式（CSS）、行为（JS）**打包成一个可复用单元：

- **输入（props）**：父传给子的只读数据，像函数的参数。
- **私有状态（state）**：组件自己管理、会随时间变化的数据。
- **输出（UI）**：根据 props + state 渲染出的界面。

好的组件遵循「单一职责 + 可组合」：小而专，像积木一样拼出复杂界面。

## 状态驱动视图

状态是 UI 的「真相之源」。当状态变化：

1. 框架检测到变化（通过 setter / 响应式代理）
2. 重新计算该渲染什么
3. 只把**变化的那部分**更新到真实 DOM（diff + 最小化操作）

你不再手写「哪里变了、怎么改」，只管「状态对不对」，渲染交给框架。

## 单向数据流

数据沿**单一方向**流动：父 → 子通过 props 下发；子想改数据，通过事件/回调**通知父**，由父改状态后再流下来。不允许多人随意直接改同一份数据。

好处是：**任意时刻的 UI 都能从状态推导出来**，调试时只要追「谁改了状态」，而非「谁动了 DOM」。这是 React/Vue 等框架可维护性的根基。

## 易错点

1. **把 props 当可变状态改**：props 是只读输入，直接改它不会反向生效且破坏数据流；要改就提升到父级或用状态。
2. **状态放错层**：状态应留在「真正需要它的最小共同父组件」，过高会无谓重渲染、过低会难以共享。
3. **用命令式思维混写**：在声明式框架里手动 `getElementById` 改 DOM，会和被框架管理的 DOM 打架，导致错乱。
4. **忽略 key**：列表渲染不写稳定 `key`，框架无法正确复用节点，出现状态错乱。

## 小结

现代前端把 UI 视为状态的函数，用组件封装结构/样式/行为，用状态驱动视图，用单向数据流保证「UI 永远可由状态推导」。这套范式把开发者从手动 DOM 同步中解放出来，专注于数据与逻辑。

## 练习

1. 用原生 JS 命令式写一个计数器（含「超过 10 变红」），再改成声明式组件写法，对比代码量与时序心智。
2. 画一张图：props 从父流向子、事件从子流回父，标出数据方向。
3. 找一个你写过的「手动同步 DOM」代码，思考如何用状态驱动改写。
