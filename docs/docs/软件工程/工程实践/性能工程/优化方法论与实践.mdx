# 优化方法论与实践

度量清楚瓶颈（见 [性能度量与剖析](/docs/软件工程/工程实践/性能工程/性能度量与剖析)）之后，才是「怎么改」。性能优化最危险的不是技术，而是**凭直觉乱改**：没定位就加缓存、没对照就重写。本章给出一套**测量驱动**的优化工作流，并按「自顶向下」的层次列出真正常生效的手段，最后用 Amdahl 定律和尾延迟放大提醒你「优化错地方等于白做」。

## 学习目标

- 复述优化工作流：测量 → 定位瓶颈 → 假设 → 改动 → 复测（且改动单一、可对照）。
- 列出从算法、数据结构，到 I/O、缓存、并发、数据库的优化层次与典型手段。
- 用 Amdahl 定律解释「为什么优化非热点收益有限」，并理解尾延迟放大效应。
- 指出过早优化、缓存踩踏（stampede）、N+1 查询等经典反模式。

## 核心概念

### 优化工作流：测量驱动，而非直觉驱动

1. **测量基线**：用分位数与吞吐建立当前表现（没有基线就没有「优化」）。
2. **定位瓶颈**：靠火焰图/剖析锁定热点——**只优化热点**，其他地方改了也不影响总时延。
3. **提出单一假设**：每次只改一个变量，否则无法判断是哪个改动起作用。
4. **改动 + 复测**：在**等价环境**下复测，确认分位数真的下降、吞吐真的上升。
5. **回归验证**：性能改动可能引入 bug 或新瓶颈，必须回归。

这条纪律的核心是：**不猜测，用数据说话**。Knuth 的名言「过早优化是万恶之源」针对的正是「没测量就优化」。

### 优化层次（自顶向下，常生效的优先）

| 层次 | 典型手段 | 收益特征 |
|------|---------|---------|
| **算法/复杂度** | 降复杂度（$O(n^2)\to O(n\log n)$）、用对数据结构 | 数量级级收益，最该先做 |
| **I/O 与批处理** | 合并请求、批量写、异步/非阻塞、流水线 | I/O 往往是最大头 |
| **缓存** | 结果缓存、CDN、缓冲池、就近计算 | 命中即对的时间近 0 |
| **并发/并行** | 多线程、无锁、减少锁竞争、避免伪共享 | 受限于临界区与核数 |
| **数据库** | 加索引、改查询、消 N+1、连接池 | 见 [查询优化](/docs/计算机科学基础/数据库系统/查询处理与优化) |
| **GC/内存/序列化** | 降分配、对象复用、高效序列化 | 长尾与吞吐的隐性杀手 |
| **网络** | 压缩、长连接/连接池、pipelining | 跨机房时显著 |

顺序不是铁律，但**先想算法与 I/O，再想缓存与并发**通常性价比最高。

### Amdahl 定律：优化非热点的天花板

若某部分占总时间比例为 $p$，将其加速 $S$ 倍，整体加速比为

$$
\text{Speedup}=\frac{1}{(1-p)+p/S}
$$

启示：**只优化占 5% 时间的部分，哪怕加速到无限倍，整体最多快 1.05 倍**。所以必须先把 $p$ 大（热点）的部分拿下。与之相对，**通用可扩展定律（USL）** 还计入「协调开销随核数增长」，解释为什么堆机器到一定程度反而变慢。

### 尾延迟放大

一个请求若需并行调用 $N$ 个下游，其**整体尾延迟 ≈ 最慢那个下游的尾延迟**。若每个下游 p99=1s，则 $N=10$ 时整体 p99 远超 1s（近似 $1-(0.99)^{10}\approx 9.6\%$ 的请求会超 1s，且实际更糟）。应对：设**更紧的下游超时 + 降级/兜底**，避免一个慢依赖拖垮整条链路。

## 示例

用 Python 演示「优化错地方（非热点）几乎无收益」，对应 Amdahl：

```python
import time

def workload():
    hot()      # 占 90% 时间的热点
    cold()     # 占 10% 时间的冷路径

def hot():
    sum(i*i for i in range(2_000_000))

def cold():
    sum(i for i in range(200_000))

# 基线
t0=time.perf_counter(); workload(); t1=time.perf_counter()
base=t1-t0

# 情形A: 把热点 hot 加速 10 倍
def hot_fast(): sum(i*i for i in range(200_000))   # 快 10x
def workload_A(): hot_fast(); cold()

# 情形B: 把冷路径 cold 加速 100 倍(看似很猛)
def cold_fast(): pass
def workload_B(): hot(); cold_fast()

tA=time.perf_counter(); workload_A(); tA=time.perf_counter()-tA
tB=time.perf_counter(); workload_B(); tB=time.perf_counter()-tB
print(f"基线={base:.3f}s")
print(f"优化热点(10x): 加速 {(base/tA):.2f}x  (接近 Amdahl 上限 1/(0.1+0.9/10)=5.26)")
print(f"优化冷路径(100x): 加速 {(base/tB):.2f}x  (仅 ~1.1x, 白费力气)")
```

## 易错点

- **过早优化**：在还没度量、没成型前就抠细节，既浪费时间又让代码复杂难维护。先正确、再清晰、最后才快。
- **优化非热点**：违反 Amdahl——把冷路径优化到极致，整体几乎不变；永远先拿热点。
- **缓存踩踏（Cache Stampede）**：缓存失效瞬间，海量请求同时击穿到后端。要用「单个请求回填 + 其他请求等待/返回旧值」或锁/singleflight 防踩踏；并设置合理 TTL 与主动刷新。
- **N+1 查询**：循环里逐条查库（1 次查列表 + N 次查详情），应是 1 次 `JOIN` 或批量 `IN`。这是 ORM 最常见的性能坑。
- **忽略尾延迟放大**：以为「每个下游 p99 都还好」，但多下游并联后整体尾延迟急剧恶化；不设置下游超时与降级会在峰值雪崩。
- **把压测环境的优化当生产结论**。环境（数据量、并发、网络）不同，最优手段会变，必须贴近生产再下定论。

## 练习

1. 某任务 60% 时间在序列化、40% 在别处。把序列化加速到原来的 4 倍，整体加速比是多少？若改为把那 40% 加速 4 倍呢？
   *答案：前者 $1/(0.4+0.6/4)=1/(0.55)=1.82$x；后者 $1/(0.6+0.4/4)=1/(0.7)=1.43$x——优化占比更大的部分收益更高。*
2. 一条请求需并行调用 5 个下游，每个独立 p99=1s。整体 p99 大约如何？如何降低？
   *提示：约 $1-(0.99)^5\approx4.9\%$ 超 1s，实际因相关性与重试更差；降低靠缩短下游 p99、设更紧超时+降级、或减少并联数。*
3. 列举三个你项目中可能存在的「N+1 查询」并说明如何改为批量/JOIN。

## 小结

性能优化要**测量驱动、单一变量、可对照复测**，绝不一上来就改。优化应按层次推进：先算法/复杂度与 I/O（数量级收益），再缓存、并发、数据库、GC/网络。**Amdahl 定律**冷酷地提醒「只优化非热点收益有限」，所以必须瞄准热点；**尾延迟放大**则警告「多下游并联会让整体尾延迟远差于单点」，需靠超时与降级兜底。经典反模式——过早优化、缓存踩踏、N+1 查询——多半源于「没先度量就动手」。整套方法与上层的 [性能度量与剖析](/docs/软件工程/工程实践/性能工程/性能度量与剖析) 与 [可观测性](/docs/软件工程/工程实践/可观测性) 共同构成性能工程闭环。
