# 包管理与依赖

## 学习目标

学完本章，你应该能够：

- 区分 `dependencies` 与 `devDependencies`
- 理解语义化版本（SemVer）与 `^` `~` `*` 的含义
- 解释 lockfile 为什么必须提交
- 知道 npm / pnpm / yarn 的核心差异

## 前置知识

在阅读下面的内容前，建议先掌握：

- [前端工程化概述](/docs/软件工程/Web前端/构建工具与工程化/前端工程化概述)

## 核心概念

包管理器负责「安装、版本解析、依赖树去重」三件事。它读取 `package.json` 中的版本范围，结合 lockfile 把依赖固定成可复现的树。

本章主线：

- 依赖的两种分类与生产/开发边界
- SemVer 与版本范围
- lockfile 的复现性
- npm / pnpm / yarn 的差异

## 依赖的分类

`package.json` 中最关键的两个字段：

```json
{
  "dependencies": {
    "react": "^18.2.0",
    "lodash": "^4.17.21"
  },
  "devDependencies": {
    "vite": "^5.0.0",
    "vitest": "^1.0.0"
  }
}
```

- `dependencies`：**运行时**也需要的包（如框架、工具库），打包后会进入产物。
- `devDependencies`：仅在**开发/构建期**需要的包（如打包器、测试器、linter），不会进生产产物。

一个易错点：把构建工具错放进 `dependencies`，会让生产环境安装一堆无用包、增大体积与攻击面。

## 语义化版本 SemVer

版本号 `主版本.次版本.补丁`（`MAJOR.MINOR.PATCH`）：

- `MAJOR`：不兼容的 API 变更
- `MINOR`：向下兼容的新功能
- `PATCH`：向下兼容的缺陷修复

版本范围符号：

| 写法 | 含义 | 示例（基线 1.2.3） |
| --- | --- | --- |
| `^1.2.3` | 允许 MINOR/PATCH 升级，不跨 MAJOR | 可装 1.9.0，不装 2.0.0 |
| `~1.2.3` | 只允许 PATCH 升级 | 可装 1.2.9，不装 1.3.0 |
| `1.2.3` | 精确锁定 | 只装 1.2.3 |
| `*` | 任意版本 | 不推荐 |

`^` 是默认行为（`npm install lodash` 会写入 `^4.17.21`）。它保证了「不会引入破坏性大版本」，但仍是**浮动范围**——不同时间安装可能得到不同补丁版本。

## lockfile 为什么必须提交

`package-lock.json`（npm）、`pnpm-lock.yaml`（pnpm）、`yarn.lock`（yarn）记录了**依赖树每一层的精确版本与哈希**。

不提交 lockfile 的后果：

- 同事 `npm install` 可能装到不同的传递依赖版本 → 「在我机器上能跑」问题
- CI 与生产构建结果不可复现
- 传递依赖被恶意篡改时无法察觉（缺少完整性哈希校验）

结论：**lockfile 必须纳入版本控制**，且生产部署用 `npm ci`（严格按 lockfile 安装、不写新锁）而非 `npm install`。

## npm / pnpm / yarn 的差异

| 工具 | 安装模型 | 特点 |
| --- | --- | --- |
| npm | 嵌套 + 扁平化 | 生态默认，速度一般 |
| yarn (classic) | 扁平化 + 并行 | 早期提速，lockfile 稳定 |
| pnpm | 全局内容寻址存储 + 硬链接 | 省磁盘、依赖严格隔离（默认不允许多版本误用） |

pnpm 的「严格隔离」是个重要差异：默认情况下，项目代码**只能访问** `package.json` 中显式声明的依赖，不能「顺手」引用未声明的传递依赖——这能提前暴露隐式耦合。

## 示例：初始化与安装

```bash
# 初始化项目
npm init -y

# 安装运行时依赖
npm install lodash

# 安装开发依赖（--save-dev 可缩写为 -D）
npm install -D vite

# 按 lockfile 精确安装（用于 CI / 生产）
npm ci
```

## 易错点

1. **`npm install` 误改 lockfile**：在 CI 用 `npm install` 可能在依赖范围允许时悄悄升级，破坏复现性；CI 一律用 `npm ci`。
2. **把锁文件加进 `.gitignore`**：等于放弃可复现构建。
3. **依赖越权**：在 pnpm 下引用了未声明的传递依赖会直接报错；在 npm/yarn 下可能「侥幸能跑」，但换环境即崩。
4. **`peerDependencies` 误解**：框架插件（如 `vite-plugin-x`）通常声明 `peerDependencies` 而非直接依赖宿主，需要你自行安装匹配的宿主版本。

## 小结

包管理器是前端工程化的地基：用 `dependencies`/`devDependencies` 划清运行与构建边界，用 SemVer 表达「能接受哪些升级」，用 lockfile 锁定可复现的依赖树。选 pnpm 可获得更严格的依赖隔离与更省的磁盘占用。

## 练习

1. 新建一个空目录，分别用 `npm` 与 `pnpm` 安装同一份 `package.json`，对比 `node_modules` 结构差异。
2. 故意把某个 `devDependency` 移到 `dependencies`，用 `npm ci` 验证生产安装是否仍成功，并思考体积差异。
3. 阅读你常用项目的 `package-lock.json`，找到一处传递依赖，确认它的精确版本与 `package.json` 中的范围如何对应。
