可读、一致的代码比「聪明」的代码更值钱。规范与重构是保持代码健康的两件工具。

## 命名与风格

- 变量/函数见名知意，避免 `tmp`、`data2` 这类含糊命名。
- 统一风格：Python 遵循 PEP 8，前端遵循团队 ESLint 配置。
- 函数短小单一职责，一个函数只做一件事。
- 命名承载意图：布尔用 `is/has/can` 前缀（`is_active`），集合用复数（`users`），避免 `data`、`info` 这类黑洞词。

## 代码评审

评审关注：正确性、可读性、边界与异常、是否有更简方案、是否引入重复。对事不对人，用建议语气。

- 好的评审意见：「这里空字符串会抛异常，要不要先判空？」——给路径。
- 差的评审意见：「这代码写得烂。」——只评价人不给方案，没人能改。

## 常见坏味道

| 坏味道 | 表现 | 方向 |
| --- | --- | --- |
| 重复代码 | 多处几乎相同的逻辑 | 提取公共函数/模块 |
| 过长函数 | 一个函数几十上百行 | 拆分成小函数 |
| 过大类 | 类承担过多职责 | 按职责拆分 |
| 过长参数列表 | 参数超过 4 个 | 封装为对象/配置 |
| 发散式变化 | 改一个需求要动多处 | 按变化轴拆分模块 |

## 重构示例：提取函数

重构前——金额、折扣、运费逻辑散落在业务函数里，难以复用也难测试：

```python
def checkout(order):
    total = 0
    for item in order.items:
        total += item.price * item.qty
    if order.user.is_vip:
        total *= 0.9
    if total > 99:
        shipping = 0
    else:
        shipping = 10
    return total + shipping
```

重构后——把「小计」「折扣」「运费」各提取为纯函数，命名即文档、便于单测：

```python
def calc_subtotal(items):
    return sum(item.price * item.qty for item in items)

def apply_vip_discount(subtotal, user):
    return subtotal * 0.9 if user.is_vip else subtotal

def calc_shipping(payable):
    return 0 if payable > 99 else 10

def checkout(order):
    subtotal = calc_subtotal(order.items)
    payable = apply_vip_discount(subtotal, order.user)
    return payable + calc_shipping(payable)
```

## 常用重构手法

- 提取函数 / 提取变量
- 内联（把过度抽象合并回去）
- 重命名（让意图更清晰）
- 以多态替代条件分支
- 引入策略模式消除长 `if/else`

## 静态分析

用工具在提交前自动发现问题：`ruff`/`flake8`（Python）、`eslint`（JS）、`golangci-lint`（Go），以及 SonarQube 做质量门禁。

:::tip
小步重构、配齐测试，远比「推倒重写」安全。
:::

## 易错点

- **过度抽象**：为「将来可能复用」提前抽三层基类，调用链反而难追踪。先写直白代码，重复两次再抽。
- **只重命名不重结构**：名字改清楚了，函数依旧做五件事，可读性没实质提升。
- **重构不带测试**：没有测试保护网下大改，回归 bug 往往在发布后才暴露。

## 练习

找出下面函数的坏味道并重写为小函数组合（提示：过长函数 + 重复 + 布尔参数坏味）：

```python
def process(data, flag):
    res = []
    for d in data:
        if flag:
            if d > 0:
                res.append(d * 2)
        else:
            if d > 0:
                res.append(d + 1)
    return res
```
