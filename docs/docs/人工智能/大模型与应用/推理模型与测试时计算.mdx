# 推理模型与测试时计算

- 在工程中判断何时该用推理模型、何时反而该避免

## 核心概念

**推理模型**指一类经过强化学习“学会逐步思考”的大模型：在给出最终答案前，先生成一段被刻意拉长、显式或隐式的**思考过程**（thinking token），再据此输出结果。代表是 OpenAI o1/o3、DeepSeek-R1、Qwen-QwQ 等。

关键思想有三条：

1. **思维链（Chain-of-Thought, CoT）**：把“直接要答案”变成“先一步步推导”。少量示例提示即可触发，但推理模型把这一步内化进权重，无需手工写示例。
2. **测试时计算扩展（test-time / inference-time compute scaling）**：传统扩展法则是“堆训练算力”（更多的参数、更多的数据）；新范式发现，在**推理阶段**给模型更多计算（更长的思考链、更多的候选采样、搜索），同样能换来 accuracy 提升。这意味着“同样的模型，想得更久就更强”。
3. **过程奖励引导**：用 [过程奖励模型（PRM）](/docs/人工智能/大模型与应用/过程奖励模型与可扩展监督) 在每一步推理上给分，让强化学习优化的不是“最终答案对不对”，而是“推理路径合不合理”，显著缓解答案对了但过程瞎编的问题。

本章主线：
- 从 CoT 到推理模型：为什么“想得久”有效
- 测试时计算 Scaling Law：推理算力也是一种资源
- o1 / R1 的训练范式：冷启动 SFT → 大规模 RL → 拒绝采样 → 再 RL
- 使用陷阱：不是所有任务都值得“深思熟虑”

## 为什么“想得久”有效

很多难题（数学、代码、多步逻辑）的失败，不是模型“不会”，而是它急于在第一个 token 就下结论，把长链条压成一步跳跃，中间任何一环出错就全盘皆输。把思考显式化后：

- 错误更容易被后续步骤自检出来（"等等，这里除零了"）；
- 模型可以把一个大问题拆成子问题分别处理；
- 强化学习能针对"过程"而非"结果"给奖励，训练信号更稠密。

一种直觉：推理模型把一部分"搜索"从训练时挪到了推理时——训练时学会"怎么思考的通用策略"，推理时把算力花在"对这道具体题实际搜一遍"。

## 典型训练流程（以 R1 范式为例）

```text
1) 冷启动 SFT（Cold-start）
   用少量高质量、带长链思考的人类/强模型示范数据微调，
   让模型先"学会说人话的思考过程"，避免一上来 RL 就语无伦次。

2) 面向推理的 RL（Reasoning RL）
   在可自动验证的领域（数学、代码）用规则或 PRM 给奖励，
   强化"长链 + 正确答案"的策略，提升推理能力。

3) 拒绝采样 + SFT（Rejection Sampling）
   用上一步模型采样大量轨迹，只保留正确且过程良好的，
   再混入写作、事实问答等通用数据做 SFT，恢复通用能力。

4) 全场景 RL（RL for all scenarios）
   用偏好奖励（有用性、安全性）再做一轮 RL，
   对齐人类偏好，同时保持推理能力。
```

## 测试时计算有哪些“花式”

除了“拉长思考链”，工程上还能这样在推理阶段换 accuracy：

- **自洽性解码（Self-Consistency）**：对同一题采样多条推理路径，投票选出现最多的答案，比单条 greedy 更稳。
- **Best-of-N + 验证器**：生成 N 个候选，用一个 reward model 或真实测试用例挑最好的。
- **推理时搜索**：把推理步骤建模成树/图，用 PRM 做节点评分、beam search 或蒙特卡洛树搜索（MCTS）挑最优路径。
- **自适应计算**：简单题少想、难题多想（模型自己决定思考长度），节省成本。

> 这呼应了 [过程奖励模型与可扩展监督](/docs/人工智能/大模型与应用/过程奖励模型与可扩展监督) 中“逐步打分”的思路——验证器越强，推理时搜索的收益越大。

## 示例：一个最小的自我一致性推理

```python
import random

def solve_with_cot(prompt, model, n=5, sample=True):
    """对同一个问题采样 n 条带思维链的解答，投票选答案。"""
    answers = []
    for _ in range(n):
        # 提示模型"一步步思考"，并开启采样以获得多样性
        out = model.generate(
            prompt + "\n请一步步思考再给答案。",
            temperature=0.7 if sample else 0.0,
            max_new_tokens=1024,
        )
        answers.append(extract_final_answer(out))
    # 多数投票
    return max(set(answers), key=answers.count)

# 注意：thinking 越长、候选越多，单次请求成本越高，
# 但换来更稳定的解答——这就是 test-time compute 的权衡。
```

## 易错点

- **简单任务别上推理模型**：对"把这句翻译成英文"这类任务，长思考链只会更慢、更贵，有时还因过度思考而答偏。按任务难度选模型。
- **thinking token 会泄露且占上下文**：思考过程可能包含错误信息、内部计划甚至敏感内容，对外展示前需要裁剪；它也计入上下文与计费。
- **长链会累积误差**：推理步数越多，越容易在中间某步“想歪”并把错误带到底；强验证器/搜索能缓解但不能根除。
- **“会思考”不等于“不幻觉”**：推理模型照样会编造定理、代码 API、引用；可验证领域（数学/代码）收益最大，开放问答收益有限。
- **成本与延迟**：测试时计算本质是“用钱/时间换准确率”，上线前务必在延迟预算和准确率增益之间做 ROI 评估。

## 练习

1. 对比同一道数学题在“直接回答”和“先 CoT 再回答”下的表现差异，记录思考链带来的变化。
2. 用上面的 `solve_with_cot` 思路，设计一个“用单元测试作为验证器”的 Best-of-N 版本（提示：用代码执行结果代替投票）。
3. 找一个你常用的模型，分别用“推理模式”和“普通模式”解一道多步逻辑题，比较两者思考过程与最终答案。

## 小结

推理模型通过强化学习把“逐步思考”内化为能力，把一部分搜索从训练时转移到推理时；**测试时计算扩展**成为继预训练扩展后的新杠杆。它大幅提升了数学、代码、复杂逻辑等可验证任务的准确率，但代价是更慢、更贵，且对开放问答收益有限。合理使用的关键，是按任务难度与延迟预算做选择。
