# 代码智能与 AI 编程

## 学习目标

## 核心概念

**代码智能（Code Intelligence）**指用大模型理解与生成程序的综合能力。它沿着三条线索演进：

1. **代码补全 → 代码生成**：从 IDE 里“下一行提示”（GitHub Copilot 早期形态），到“按自然语言写一整个函数/脚本”。底层是 Codex、StarCoder、DeepSeek-Coder、Qwen-Coder、CodeLlama 等**代码大模型**，通常在海量代码语料上继续预训练，并善于处理 AST、长上下文与多文件结构。
2. **仓库级理解（repo-level）**：真实任务不是“写孤立函数”，而是“在百万行仓库里改一处并联动其他文件”。这需要把相关文件/符号**检索**进上下文（用向量库或语法索引找相似代码、调用关系），再让模型基于全局信息编辑。
3. **代码智能体（code agent）**：模型不只是出代码，而是**自己跑流程**——定位 Bug（`grep`/读栈）、改文件、执行测试、看失败、再改。代表如 SWE-agent、Devin。它把 [Agent 的“规划-工具-反馈”循环](/docs/人工智能/大模型与应用/Agent开发) 落到了软件工程场景。

## 能力边界：补全、生成、智能体

| 形态 | 输入 | 输出 | 是否需要执行环境 |
|------|------|------|------------------|
| 代码补全 | 光标前若干行 | 下一片段 | 否 |
| 代码生成 | 自然语言需求 | 完整函数/模块 | 否（但建议验证） |
| 代码智能体 | Issue / 缺陷描述 | 多文件补丁 + 测试通过 | 是（沙箱/CI） |

> 关键认知：**模型默认不会运行代码**。它能写出看似正确的程序，但无法自行验证。要让它“真的会改仓库”，必须给它工具——读文件、跑测试、查日志，形成反馈闭环。

## 示例：一个最小代码智能体循环

```python
def code_agent(issue, repo, model, max_steps=10):
    context = repo.retrieve(issue)          # 1) 检索相关文件/符号（RAG）
    for step in range(max_steps):
        # 2) 模型基于上下文决定“下一步动作”
        action = model.plan(context, issue)
        if action.type == "edit":
            repo.apply_patch(action.patch)   # 3) 执行动作
        elif action.type == "run_tests":
            result = repo.run(action.cmd)    # 3) 用真实执行获取反馈
            context += f"测试输出:\n{result}"
        if action.type == "done":
            return repo.diff()               # 4) 产出补丁
    return repo.diff()
```

这里每一步都依赖**真实执行结果**作为反馈——这正是代码智能体区别于“一次性生成”的核心。

## 基准在衡量什么

- **HumanEval / MBPP**：给函数签名与文档串，模型补全实现，用隐藏单元测试判对错。衡量“单函数生成”，但容易被记忆/数据污染影响。
- **SWE-bench**：用真实 GitHub Issue + PR 构造任务，模型需产出能通过该仓库既有测试的补丁。衡量“仓库级、端到端”的工程能力，更贴近现实，但构建成本高、且依赖测试是否充足。
- **LiveCodeBench / BigCode 等**：持续更新的竞技编程/多语言基准，缓解“刷榜污染”。

> 注意：测试通过 ≠ 语义正确。测试只覆盖了编写者想到的情形；模型可能用“恰好过测试”的取巧实现绕过真实需求。

## 易错点

- **模型不会自己跑代码**：不接工具/沙箱就当“能改仓库”用，会得到未经验证、甚至无法运行的代码。务必闭环验证。
- **上下文窗口装不下整个仓库**：百万行项目不能全塞进 prompt，必须靠检索（RAG/语法索引）精准召回相关片段，否则模型“看不见”关键定义。
- **测试通过不等于正确**：模型可能拟合测试而非需求；评审时仍要人看逻辑与边界。
- **许可证与合规风险**：训练语料包含 GPL/专有代码，生成物的许可归属、是否能商用需评估；企业场景要开溯源与过滤。
- **安全反模式**：代码模型可能生成含 SQL 注入、命令注入、硬编码密钥的“能跑但有漏洞”的代码——需要安全扫描而非只看功能。

## 练习

1. 用一个代码模型，分别“不带上下文”和“给它相关依赖文件”两种方式让它补全一个调用了某库的函数，对比正确性。
2. 设计一个“用单元测试作为验证器”的代码智能体（提示：把测试失败信息回灌给模型做下一轮修订）。
3. 找一道 SWE-bench 风格的小 Issue，手动走一遍“定位文件 → 改代码 → 跑测试 → 修正”的闭环，体会工具反馈的价值。

## 小结

代码智能从“补全”走向“生成”再走向“智能体”，本质是不断把**外部工具与执行反馈**接入模型。仓库级任务靠检索增强补全局视野，代码智能体靠“定位-编辑-验证”闭环把一次性输出变成可迭代的工程动作。落地时务必正视许可、安全与“测试通过≠正确”的局限。
