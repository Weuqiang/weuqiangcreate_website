# 查询处理与优化

你写一句 `SELECT ... JOIN ... WHERE ...`，数据库并不会「按字面顺序执行」。它先解析成**逻辑计划**，再枚举**物理执行路径**，用**代价模型**挑一条「预计最便宜」的——这就是查询优化器。理解它，你才能写出优化器帮得上忙的 SQL，也才看得懂 `EXPLAIN`。本章承接 [存储引擎与索引](/docs/计算机科学基础/数据库系统/存储引擎与索引)，讲清执行与优化。

## 学习目标

- 描述查询处理流水线：解析 → 逻辑计划 → 代价估算 → 物理计划 → 执行。
- 比较三种连接算法（嵌套循环 / 排序归并 / 哈希连接）的复杂度与适用场景。
- 理解基于代价优化（CBO）如何靠统计信息估算行数与选择性。
- 能解释常见「慢查询」的根因（坏连接顺序、缺失统计、索引失效）。

## 核心概念

### 查询处理流水线

1. **解析与重写**：词法/语法分析成解析树，做语义检查（表/列是否存在）。
2. **生成逻辑计划**：转为关系代数表达式（选择、投影、连接、聚合）。
3. **代价估算**：基于**统计信息**（表行数、列基数、直方图、索引）估算每个算子的输出行数（基数）与 I/O/CPU 成本。
4. **计划枚举与搜索**：对逻辑计划应用等价变换（连接重排、谓词下推），枚举候选物理计划，按代价选最优。
5. **执行**：用火山模型（iterator 逐行 `Next()`）或向量化方式跑物理计划。

### 连接算法

连接是 OLTP/OLAP 中最贵的操作之一，三种主流算法各有适用：

| 算法 | 思想 | 复杂度 | 适用 |
|------|------|--------|------|
| **嵌套循环（NLJ）** | 外层每一行扫内层全表 | $O(R\cdot S)$ | 内层有索引（Index NLJ）时极佳 |
| **排序归并（Sort-Merge）** | 两边排序后游标归并 | $O(R\log R+S\log S)$ | 双方已排序/有有序索引、大表对等连接 |
| **哈希连接（Hash Join）** | 小表建哈希表，大表探测 | $O(R+S)$ | 无索引的大表等值连接（默认首选） |

**Index Nested Loop** 是「小表 × 大表索引」的黄金组合：外层小、内层靠 B+ 树索引定位，几乎免全扫。**Hash Join** 在无索引的大表等值连接中最快；**Sort-Merge** 在双方本就有序或需去重时占优。

### 基于代价优化（CBO）

优化器的核心是**估算「中间结果有多大」**。它用：

- **表统计**：行数、页数的估计。
- **列统计**：基数（distinct 值）、直方图（值分布）、NULL 比例。
- **选择性（Selectivity）**：谓词 `col = 5` 过滤掉多少比例的行。等值谓词选择性 $\approx 1/\text{distinct}(col)$。

有了基数，就把逻辑计划各算子的 I/O（按 [存储引擎](/docs/计算机科学基础/数据库系统/存储引擎与索引) 的「碰多少页」）与 CPU 成本相加，选总代价最小的连接顺序与算法。**统计信息过期**是慢查询的头号原因——`ANALYZE` 更新的统计让优化器「看清楚」数据。

### EXPLAIN 示例

```sql
-- 查看执行计划（Postgres 风格）
EXPLAIN ANALYZE
SELECT o.id, c.name
FROM orders o
JOIN customers c ON o.cust_id = c.id
WHERE o.total > 1000;
-- 关注: 是否用了索引扫描? 实际行数 vs 估计行数(偏差大说明统计过期)
--       JOIN 顺序是否把小表放内层?
```

## 最小示例

用 Python 对比三种连接算法的实际开销，体会「数据特征决定算法选择」：

```python
import time

def nlj(R, S):                       # 朴素嵌套循环 O(|R||S|)
    return sum(1 for r in R for s in S if r == s)

def hash_join(R, S):                 # 哈希连接 O(|R|+|S|)
    h = set(R)
    return sum(1 for s in S if s in h)

R = list(range(10000))
S = list(range(5000, 15000))         # 与 R 有 5000 个重叠

t0=time.perf_counter(); nlj(R,S); t1=time.perf_counter()
t2=time.perf_counter(); hash_join(R,S); t3=time.perf_counter()
print(f"嵌套循环: {t1-t0:.4f}s  (随两表乘积增长)")
print(f"哈希连接: {t3-t2:.4f}s  (随两表之和增长, 大表时碾压)")
```

## 易错点

- **迷信「SQL 写法顺序 = 执行顺序」**。SQL 是声明式的，优化器会重排连接顺序、下推谓词；你写的 `FROM` 顺序不等于实际执行顺序。
- **缺统计信息导致坏计划**。刚灌入大量数据没 `ANALYZE`，优化器按旧统计选错连接顺序或放弃索引，查询暴慢。
- **对索引列套函数**。`WHERE YEAR(created_at)=2026` 会让 B+ 树索引失效（变成对每行算函数），应改成范围条件 `created_at BETWEEN ...`。
- **隐式类型转换**。字符串列与数字比较会触发转换、放弃索引，甚至改变语义——务必类型匹配。
- **只看「逻辑正确」不看计划**。同一结果的不同写法代价可能差万倍；上线前用 `EXPLAIN` 验证是否走索引、连接顺序是否合理。

## 练习

1. 两表 R(100万行)、S(1000行)，在 `R.id = S.id` 上连接，且无索引。优化器大概率选哪种算法？为什么？
   *提示：Hash Join 对无索引大表最优；也可 Index NLJ（若 R 有索引）；Sort-Merge 需先排序，代价高。*
2. 某查询 `EXPLAIN` 显示「估计行数 1000，实际 100 万」，最可能不是哪种原因？
   *答案：统计信息过期/缺失（最常见）；也可能是相关性强的列组合、或缺少直方图导致选择性估错。*
3. 为什么 `WHERE col*2 > 10` 比 `WHERE col > 5` 更难用上索引？如何改写？

## 小结

查询处理把 SQL 解析为逻辑计划，再由基于代价的优化器枚举物理路径、按统计信息估算基数与 I/O 选最优。连接算法中，Index NLJ 适合「小表×有索引大表」，Hash Join 适合无索引大表等值连接，Sort-Merge 适合已排序场景。优化器的「眼睛」是统计信息——过期统计会选错计划，是慢查询头号根因。写 SQL 时应配合 `EXPLAIN` 验证索引使用与连接顺序，避免对索引列套函数、隐式类型转换等让索引失效的写法。查询正确性最终还要靠 [事务并发与恢复](/docs/计算机科学基础/数据库系统/事务并发与恢复) 兜底。
