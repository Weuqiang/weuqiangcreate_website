# 存储引擎与索引

逻辑层（[关系模型与 SQL](/docs/计算机科学基础/数据库系统/关系模型与SQL)）只管「数据长什么样」，物理层才决定「数据怎么落盘、怎么被快速找到」。存储引擎是数据库的心脏：它管理磁盘页、把记录组织成可检索的结构、用缓冲池弥合内存与磁盘的速度鸿沟。本章讲清两类主流索引范式——**读优化的 B+ 树**与**写优化的 LSM 树**，以及它们各自的取舍。

## 学习目标

- 理解页式存储（page/block）与记录布局，为什么数据库以「页」为单位读写。
- 说清 B+ 树为什么适合范围查询，以及它与二叉搜索树、哈希的根本区别。
- 对比 LSM 树（写优化、SSTable + 压实）与 B+ 树（读优化）的取舍。
- 解释缓冲池、覆盖索引、聚簇/非聚簇索引对性能的影响。

## 核心概念

### 页式存储：数据库的 I/O 单位

磁盘按**页（page，通常 4KB–16KB）**读写，不能按「一行」随机读。记录被打包进页，页是内存与磁盘之间交换的最小单位。数据库的几乎所有成本模型都围绕「**这次操作要碰多少页**」展开——减少随机 I/O、增加顺序 I/O 是性能优化的总纲。

### B+ 树：读优化的索引范式

B+ 树是多路平衡搜索树，几乎所有关系型数据库（Postgres/MySQL/SQL Server）的默认索引：

- **所有数据只存在叶子层**，且叶子用指针串成**有序链表** → 范围查询 `WHERE id BETWEEN a AND b` 只需顺链表扫，极其高效。
- 内部节点只存「路由键 + 子指针」，扇出（fan-out）大，树高低（千万级数据也只需 3–4 层）→ 一次点查约 3–4 次 I/O。
- 插入/删除通过节点分裂与合并保持平衡，维护成本可控。

B+ 树同时支撑**等值查询**与**范围查询**，是「通用索引」的首选。

### LSM 树：写优化的索引范式

日志结构合并树（Log-Structured Merge-tree）为**高写入吞吐**设计（LevelDB/RocksDB/Cassandra/HBase）：

- 写入先进内存的 **MemTable**，并追加到磁盘 **WAL**（防丢）；MemTable 写满后刷成不可变的 **SSTable** 文件。
- 读需合并内存与多层 SSTable（可能多路归并），因此**读放大**较高；用 **Bloom Filter** 跳过必然不含目标的 SSTable。
- 后台 **Compaction（压实）** 把多层 SSTable 合并去重、回收空间，控制读放大与空间放大。

**B+ 树 vs LSM 树的核心取舍**：B+ 树读稳定、写有随机 I/O（刷页）；LSM 树写吞吐极高（顺序追加）、但读有放大、且有压实开销。简单说——**读多写少用 B+ 树，写多读少用 LSM**。

### 哈希索引与其他

- **哈希索引**：仅适合等值查询（`=`），O(1) 但**不支持范围**与排序，常用于内存表或 LSM 的辅助结构。
- **聚簇索引（Clustered）**：叶子直接存整行数据（如 MySQL InnoDB 的主键），主键查找最快；**非聚簇索引**叶子存「主键值」再回表。
- **覆盖索引**：索引本身包含查询所需全部列，无需回表，显著加速。

### 缓冲池（Buffer Pool）

内存中缓存热点页，命中则免磁盘 I/O。置换策略常用 LRU 的变种（避免全表扫描污染缓存）。缓冲池命中率是数据库性能最关键指标之一。

## 最小示例

用 Python 演示「范围查询在 B+ 树式有序存储上多么便宜」，并与无序（全扫）对比：

```python
import bisect, random, time

# 模拟 100 万行的主键，已按 B+ 树叶子链表那样有序存储
n = 1_000_000
rows = sorted(random.sample(range(10*n), n))

def range_query_btree(a, b):
    # 二分定位起点 + 顺序扫（B+ 树范围查询的抽象）
    lo = bisect.bisect_left(rows, a)
    hi = bisect.bisect_right(rows, b)
    return hi - lo

def range_query_scan(a, b):
    # 无序/无索引：必须全表扫描
    return sum(1 for x in rows if a <= x <= b)

# 范围 [400000, 400999] 共 1000 行
t0 = time.perf_counter(); cnt1 = range_query_btree(400000, 400999); t1 = time.perf_counter()
t2 = time.perf_counter(); cnt2 = range_query_scan(400000, 400999); t3 = time.perf_counter()
print(f"B+树式: 命中 {cnt1} 行, 耗时 {t1-t0:.6f}s")
print(f"全表扫描: 命中 {cnt2} 行, 耗时 {t3-t2:.6f}s (随数据量线性增长)")
```

要点：有序索引把「范围查询」从 $O(N)$ 全扫降为 $O(\log N + k)$，这就是索引价值的本质。

## 易错点

- **以为索引「越多越好」**。每个索引都拖慢写入（要同步维护）并占空间；写多场景下过多索引会严重拖累吞吐。
- **范围查询用哈希索引**。哈希不支持 `<`、`BETWEEN`、排序，期望范围扫描却建了哈希索引会退化成全扫。
- **在非聚簇索引上「回表」失控**。只 `SELECT` 索引列才能命中覆盖索引；`SELECT *` 常导致回表，抵消索引收益。
- **忽略索引选择性**。对「性别」这种低基数列建索引几乎无益（优化器可能直接弃用），高基数列才值得。
- **混淆 LSM 的「写快」与「读也快」**。LSM 牺牲了读放大与压实成本换写入吞吐；读多场景盲目上 LSM 反而变慢。

## 练习

1. 一张 1 亿行的表，B+ 树索引扇出为 200，点查最多需要几次 I/O？若把扇出降到 50 呢？
   *提示：树高 $\approx \log_{fanout}(N)$；扇出 200 时约 $\log_{200}(10^8)\approx3.3$→4 层，扇出 50 时约 $\log_{50}(10^8)\approx4.6$→5 层。*
2. 为什么 LSM 树读放大严重？Bloom Filter 与 Compaction 分别缓解哪类问题？
3. 聚簇索引下，若主键是随机 UUID 而非自增整数，写入性能会怎样变化？为什么？
   *提示：UUID 使新插入散落到各处，B+ 树页分裂频繁、缓存局部性差，写放大明显；自增则顺序追加。*

## 小结

数据库以「页」为 I/O 单位，所有成本都围绕「碰多少页」。**B+ 树**把数据放在有序叶子链表上，点查与范围查询都高效，是读优化的通用索引；**LSM 树**用内存 MemTable + 顺序追加的 SSTable + 后台压实，换取极高写吞吐，但带来读放大（靠 Bloom Filter 缓解）。哈希索引仅适合等值、不支持范围。聚簇/覆盖索引与缓冲池命中率共同决定实际性能。选择哪种引擎本质是**读写取舍**——这直接与上层 [查询处理与优化](/docs/计算机科学基础/数据库系统/查询处理与优化) 的执行代价模型相连。
