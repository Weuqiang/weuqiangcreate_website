## 核心概念

### 为什么分布式这么难

单机程序假设「CPU、内存、时钟都可靠且共享」。分布式系统打破这三条假设：

1. **部分失败**：一台机器宕机，其他还在跑——你无法「立刻知道」谁还活着。
2. **网络不可靠**：消息可能丢失、重复、乱序、延迟；「超时」到底是机器挂了还是只是慢，无法区分。
3. **没有全局时钟**：各机时钟漂移，「事件 A 先于 B」不能靠墙钟判断。

这三条让「达成一致」变成难题。

### CAP 定理

给定**分区容错（P）**不可避免（网络一定会偶尔断），系统只能在**一致性（C）**与**可用性（A）**间取舍：

- **CP**：分区时牺牲可用性，保证数据一致（如 ZooKeeper、etcd 在选主期间拒绝写入）。
- **AP**：分区时继续服务，但可能返回过期数据（如许多缓存/NoSQL 在最终一致下可用）。

> 注意：CAP 说的是「分区发生时」的取舍，不是「平时二选一」。多数互联网系统选 AP + 最终一致，金融核心选 CP。

### 一致性模型（强度光谱）

- **线性一致（强一致）**：所有读都看到「最新一次写」，如同单机。代价最高。
- **因果一致**：有因果关系的操作保序，无因果的可以乱序——比强一致松、比最终一致强。
- **最终一致**：只要不再写入，一段时间后所有副本会一致。高可用系统的常见选择（DNS、CDN、很多 NoSQL）。

### 时间与时钟

既然没有全局时钟，如何判断事件先后？

- **Lamport 逻辑时钟**：给事件标递增计数器，用「happened-before」关系排偏序，能区分因果，但区分不了并发。
- **向量时钟**：每个进程维护向量，能**判断两个事件是否并发**（无法比较则必并发）——用于检测冲突。
- **TrueTime / HLC**：用时钟不确定区间或混合逻辑物理时钟，逼近「带误差的全局时间」。

### 共识：让一堆机器「意见一致」

共识（Consensus）指：即便有节点崩溃、消息延迟，存活节点仍能对某个值达成一致。难点由 **FLP 不可能定理**揭示：在异步网络+一个崩溃的模型中，**不存在 deterministic 的共识算法能保证有限时间终止**。于是实际算法（Paxos、Raft）要么放宽（用领导者的同步假设），要么用随机化/超时。

- **Raft**（为可理解性设计）：核心是**领导者选举 + 日志复制**。一个任期选出一个 Leader，所有写先到 Leader，Leader 把日志复制到多数派（quorum）才算提交；Leader 挂了就触发新选举。
- **Paxos**：更早、更精炼但更难懂；Raft 可视为其工程化重构。

### 容错复制

为了高可用，数据要在多副本间复制：

- **主从复制**：一写多读，主挂了提一个从。
- **quorum（法定人数）**：写需 $W$ 个副本确认、读需 $R$ 个，且 $W+R>N$ 保证读写交集——既能容错又能控一致性强度。
- **Zab / ZK**：ZooKeeper 用的原子广播协议，保证全序广播，是很多分布式协调的基础。

## 示例

Raft 领导者选举的最小心智模型（伪代码）：

```python
class Node:
    def __init__(self):
        self.role = "follower"
        self.current_term = 0
        self.leader = None

    def on_timeout(self):                    # 选举超时：没收到 Leader 心跳
        self.current_term += 1
        self.role = "candidate"
        votes = self.request_votes(self.current_term)   # 向其他节点要票
        if votes > len(ALL_NODES) // 2:      # 拿到多数派
            self.role = "leader"
            self.leader = self.id

    def on_append_entries(self, term, leader_id):
        if term >= self.current_term:        # 收到合法 Leader 心跳
            self.role = "follower"           # 退让，避免分裂投票
            self.leader = leader_id
```

要点：**多数派（quorum）**是容错的核心——只要活着的节点能凑成多数，系统就能继续选出 Leader 并达成一致。

## 易错点

- **误以为「超时=对方挂了」**：超时只说明「暂时联系不上」，可能是网络慢；草率宣布节点死亡会引发脑裂。
- **混淆 CAP 的「平时」与「分区时」**：CAP 只在网络分区发生时才强制 C/A 取舍，常态两者可兼得。
- **把最终一致当地强一致用**：读到了过期数据就报 bug——要按一致性模型设计业务（如读己之写）。
- **忽视 FLP 不可能**：别指望有一个「永远有限时间终止」的纯异步共识；实际系统都靠超时/领导者等放宽。

## 练习

1. 用 CAP 解释：为什么 etcd/Redis（强一致配置存储）在选主期间会拒绝写入，而 Cassandra（AP）会继续服务。
2. 向量时钟如何判断两个事件是「并发」而非「有先后」？
3. Raft 中为什么「日志复制到多数派」就算提交？少数派副本宕机为何不影响安全？

## 小结

分布式系统研究如何在**部分失败、网络不可靠、无全局时钟**之上构建可靠服务。核心结论：**CAP 在分区时必须 C/A 取舍**；一致性有强→因果→最终的强度光谱；**Lamport/向量时钟**解决事件排序；**Raft/Paxos** 在 FLP 不可能的阴影下用「多数派+领导者」实现共识；**quorum 复制**兼顾容错与一致性强度。它与[微服务与分布式架构](/docs/软件工程/工程实践/微服务与分布式架构)（应用层）和[进程线程调度](/docs/计算机科学基础/操作系统/进程线程与调度)（单机并发）上下衔接。
