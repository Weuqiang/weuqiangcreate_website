## 核心概念

### 监控 ≠ 可观测性

- **监控（Monitoring）**：基于「已知未知」——你预先知道要盯什么（CPU、错误率），设阈值报警。适合稳定、可预测的系统。
- **可观测性（Observability）**：基于「未知未知」——系统出你没预料的故障时，仍能通过它**输出的信号推断内部状态**。源自控制论：系统可被「从外部输出推断内部」的程度。

现代系统（微服务、异步、多租户）故障模式千奇百怪，靠预置仪表盘不够，需要能**临场下钻**的能力。

### 三大支柱

| 支柱 | 回答的问题 | 形态 |
|------|-----------|------|
| **日志（Logs）** | 当时发生了什么（细节） | 结构化事件（JSON），含 trace_id 关联 |
| **指标（Metrics）** | 系统整体健康如何（聚合） | 计数器/仪表/直方图，带时间戳与标签 |
| **链路追踪（Traces）** | 一次请求穿过了哪些服务、各花多久 | 由 span 组成的调用树，跨服务串联 |

三者靠 **trace_id / span_id** 关联：一个请求从网关到数据库，每个环节的日志和指标都带上同一个 trace_id，才能拼出全貌。

### SLI / SLO / 错误预算

- **SLI（服务质量指标）**：可量化的真实体验，如「请求成功率」「P99 延迟」。
- **SLO（目标）**：对 SLI 的承诺，如「99.9% 请求 < 300ms」。SLO 是产品/工程之间的契约。
- **错误预算（Error Budget）**：「允许的失败额度」= 1 − SLO。预算充足可放心发布；预算快烧完则收紧变更——用数据而非直觉决定「能不能发」。

### 工具栈与 OpenTelemetry

- **指标**：Prometheus 拉取 + Grafana 展示；用 PromQL 查询。
- **日志**：ELK（Elasticsearch/Logstash/Kibana）或 Loki，结构化检索。
- **追踪**：Jaeger / Tempo，可视化调用链。
- **OpenTelemetry（OTel）**：厂商中立的**采集标准**，统一生成 logs/metrics/traces，再导出到任意后端——避免被单一 APM 厂商锁定。

### 与 CI/CD、测试的关系

可观测性不是「上线后才做的事」：质量应**左移**（测试/TDD 在开发期拦截）+ **右移**（可观测性在生产期发现）。CI/CD 发布时联动：灰度发布 + 实时观测关键 SLI，异常自动回滚。

## 示例

一段带 trace_id 的结构化日志，以及把它连成链路的思路：

```json
{
  "ts": "2026-08-06T10:00:01Z",
  "level": "warn",
  "service": "order",
  "trace_id": "a1b2c3",
  "span_id": "s07",
  "msg": "payment gateway latency high",
  "p99_ms": 820
}
```

配合追踪，一次跨服务的慢请求会被还原成调用树：

```
GET /checkout  (trace a1b2c3)
├─ auth     12ms
├─ cart     30ms
├─ order   110ms
│  └─ payment  (span s07) 820ms  ← 瓶颈在此，靠 trace_id 串联定位
└─ notify    20ms
```

要点：**trace_id 是三支柱的胶水**——没有它，日志、指标、追踪各说各话，无法定位跨服务问题。

## 易错点

- **只堆仪表盘不算可观测**：若只能看预设图表，遇到新故障仍两眼一抹黑；要能按需下钻、按 trace_id 串联。
- **日志不结构化、无关联 ID**：纯文本日志无法检索关联，出问题难拼全貌；务必结构化并带 trace_id。
- **SLO 设得太松或太紧**：太松没意义，太紧则团队疲于救火；错误预算要对齐业务真实体验。
- **把追踪当日志用**：trace 看「跨服务路径与耗时」，日志看「单点细节」，指标看「整体趋势」，三者职责不同不可互相替代。

## 练习

1. 举例说明一个「监控能发现、但无法定位根因」的场景，以及可观测性如何补齐。
2. 为什么 trace_id 是三大支柱的胶水？没有它跨服务排障会怎样？
3. 给定 SLO「99.9% 成功率」，计算一个月的错误预算（允许失败请求数），并说明预算耗尽后该怎么做。

## 小结

可观测性让你在**没预料的故障**中也能推断系统内部状态，靠**日志/指标/链路追踪**三大支柱，并以 **trace_id** 串联。SLI/SLO/错误预算把「能不能发版」变成数据决策；OpenTelemetry 统一采集避免厂商锁定。它与[持续集成与部署](/docs/软件工程/工程实践/持续集成与部署)、[自动化测试](/docs/软件工程/工程实践/自动化测试与TDD)共同构成「左移质量 + 右移可观测」的完整工程闭环，也是排查[消息队列](/docs/软件工程/后端通识/消息队列)等异步链路问题的关键。
