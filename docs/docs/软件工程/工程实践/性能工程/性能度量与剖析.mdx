# 性能度量与剖析

性能优化的第一步不是改代码，而是**把「慢」量化成可比较的指标**。很多人凭感觉优化，结果「优化」后反而更慢——因为没度量、没对照。本章建立正确的度量语言（延迟/吞吐/分位数），并介绍找到热点的剖析（profiling）与压测方法。它是 [优化方法论与实践](/docs/软件工程/工程实践/性能工程/优化方法论与实践) 的前置。

## 学习目标

- 区分延迟与吞吐，理解为什么「看平均值不够，必须看分位数（p95/p99）」。
- 用 Little 定律把「并发数、吞吐、延迟」三者联系起来。
- 说出 CPU 采样剖析、内存剖析、Off-CPU 剖析各自解决哪类问题，以及火焰图怎么读。
- 设计严谨的基准测试与压测，避开预热不足、方差过大等常见陷阱。

## 核心概念

### 延迟 vs 吞吐，以及为什么看分位数

- **延迟（Latency）**：单个请求花多久（如 120ms）。**吞吐（Throughput）**：单位时间处理多少（如 800 req/s）。
- **平均值会骗人**：100 个请求平均 50ms，可能其中 99 个 10ms、1 个 5000ms——平均完全掩盖了这个「长尾」。
- **分位数（Percentile）**：p50（中位）、p95、p99、p999 表示「99% 的请求快于该值」。**尾延迟（tail latency）** 往往决定用户体验与 SLA——一次 checkout 慢 5 秒，用户不会管另外 99 次多快。
- 绝不能对分位数再求平均（先 avg 再取 p99 无意义），必须保留原始分布或用直方图聚合。

### Little 定律

稳定系统中三者满足：

$$
L=\lambda\,W
$$

- $L$：系统中平均并发数（在途请求数）
- $\lambda$：到达率（吞吐）
- $W$：平均停留时间（延迟）

用途：知道其中两个就能推第三个。例如吞吐 100 req/s、平均延迟 0.2s，则平均并发约 20。它帮你判断「瓶颈在不在并发数」。

### 剖析：找到热点

- **CPU 采样剖析（Sampling Profiler）**：按固定频率采样调用栈，热点函数被采中次数多 → 生成**火焰图**（横向宽度=耗时占比，自上而下=调用栈）。看「最宽的那一层」而非最顶层。
- **内存剖析**：追踪分配/泄漏、GC 压力；堆快照对比找泄漏对象。
- **Off-CPU 剖析**：很多慢不在 CPU，而在等锁、等 I/O、等网络——这类「不在 CPU 上跑」的时间要靠 Off-CPU / 阻塞剖析或 [追踪](/docs/软件工程/工程实践/可观测性) 抓。

### 基准测试与压测

- **微基准（Microbenchmark）**：测单函数，需**预热**（JIT 编译、缓存升温）、多次取中位数、关掉干扰进程；否则测得的是噪声。
- **负载测试（Load）**：逐步加压看吞吐拐点与延迟曲线。
- **压力/容量测试（Stress）**：压到崩溃，找系统容量上限与降级行为。
- **浸泡测试（Soak）**：长时间中压运行，暴露内存泄漏与资源耗尽。
- **尖峰测试（Spike）**：突然加卸载，验证弹性与队列缓冲。

## 示例

用 Python 演示「平均值如何掩盖尾延迟」，以及如何计算分位数：

```python
import numpy as np, time

# 模拟 1000 次请求耗时: 多数快, 偶发长尾
rng = np.random.default_rng(0)
latencies = np.concatenate([
    rng.normal(20, 5, 990),       # 990 次 ~20ms
    rng.normal(800, 100, 10),     # 10 次长尾 ~800ms
])

print(f"平均延迟   = {latencies.mean():.1f} ms")
print(f"p50/p95/p99 = {np.percentile(latencies,50):.1f} / "
      f"{np.percentile(latencies,95):.1f} / {np.percentile(latencies,99):.1f} ms")
print(f"最大延迟   = {latencies.max():.1f} ms")
# 平均 27ms 看起来很健康, 但 p99=~1000ms -> 1% 用户痛苦

# Little 定律: 吞吐 100 req/s, 平均延迟 0.027s -> 平均并发 ≈ 2.7
throughput, avg_latency = 100, latencies.mean()/1000
print(f"Little 定律: 平均并发 L = {throughput*avg_latency:.2f}")
```

## 易错点

- **只盯着平均延迟**。平均值对长尾不敏感，而 SLA/体验由 p95/p99 决定；务必报告分位数。
- **对分位数求平均**。先聚合成直方图或保留原始样本再算分位，绝不在「已平均的数」上再取百分比。
- **微基准没预热**。JIT、CPU 缓存、分支预测在热身后才稳定，冷启动测得的是初始化开销而非真实性能。
- **压测用错思考时间/并发模型**。没有「用户思考时间」的压测会把系统压出真实场景不会出现的行为；并发数≠用户数。
- **只看 CPU 火焰图**。大量延迟来自等锁/I/O（Off-CPU），在 CPU 剖析里这些时间「不在 CPU 上」反而看不见，需配合阻塞剖析与 [追踪](/docs/软件工程/工程实践/可观测性)。

## 练习

1. 系统吞吐 200 req/s，p99 延迟 1.5s，但平均延迟仅 80ms。用 Little 定律估算平均在途请求数，并说明为什么「仅看平均」会误判容量。
   *答案：L≈200×0.08=16；但 p99 下若按 1.5s 算瞬时并发可达 ~300，长尾会瞬间打满连接池/线程，平均掩盖了容量风险。*
2. 一个函数微基准显示「优化后快 2 倍」，上线却没感觉到——可能漏了什么？
   *提示：微基准可能没预热/没代表真实调用模式（缓存命中率、数据规模不同），或瓶颈根本不在这段（见 Amdahl）。*
3. 为什么不能直接 `time` 一次就下结论？严谨微基准至少要做到哪三点？
   *答案：单次含噪声与冷启动；需预热、多次取中位数/分位、隔离干扰进程并固定环境。*

## 小结

性能度量先分清**延迟与吞吐**，并用 **p95/p99 分位数**而非平均值刻画尾延迟——平均值会掩盖长尾，而长尾决定体验。Little 定律 $L=\lambda W$ 把并发、吞吐、延迟统一。剖析上，**CPU 采样 + 火焰图**找计算热点，**内存剖析**找泄漏与 GC 压力，**Off-CPU 剖析**抓「等锁/等 I/O」这类不在 CPU 上的延迟；基准与压测须预热、取分位、区分负载类型（load/stress/soak/spike）。度量清楚后，才能进入 [优化方法论与实践](/docs/软件工程/工程实践/性能工程/优化方法论与实践) 有的放矢地改。
