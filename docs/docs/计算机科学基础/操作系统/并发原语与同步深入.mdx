## 核心概念

### 为什么需要同步原语

当多个线程同时访问共享可变状态，且至少有一个在写时，**竞态（race condition）** 会让结果依赖不可控的时序。同步原语的作用就是**把「读-改-写」这样的复合操作变成原子的、或强制某种顺序**，从而恢复确定性。

### 互斥锁（Mutex）

最基础的「排他访问」原语：同一时刻只允许一个线程持锁。未获取锁的线程**阻塞**（让出 CPU，进入等待队列）。适用于临界区较长、持锁期间可能睡眠的场景。代价是上下文切换。

### 自旋锁（Spinlock）

获取锁失败时不睡眠，而是**循环忙等（spin）**。适用于临界区极短、且不允许睡眠的上下文（如中断处理、内核态）。忙等浪费 CPU，但在「马上就能拿到」的短临界区里比阻塞+唤醒便宜。

> 经验法则：临界区短且不能睡眠 → 自旋锁；临界区长或可能阻塞 → 互斥锁。

### 读写锁（RWLock）

允许多个读者**同时**读，但写者**独占**。适合「读多写少」的数据结构（配置、缓存）。注意写者饥饿问题（持续读者可能饿死写者），部分实现用「写者优先」缓解。

### 条件变量（Condition Variable）

与互斥锁配合，解决「**等待某个条件成立**」的问题。典型模式：

```cpp
std::unique_lock<std::mutex> lk(m);
cv.wait(lk, [&]{ return ready; });   // 原子地释放锁并睡眠，被唤醒后重新加锁并复查
// ... 条件满足后继续
```

`wait` 必须在循环中复查条件（避免虚假唤醒）。它与「信号量」不同：条件变量不计数，只负责「等待/通知」。

### 信号量（Semaphore）

由 Dijkstra 提出，维护一个**计数**。P（wait）递减，若为负则阻塞；V（signal）递增并唤醒。二值信号量可当锁用，**计数信号量**常用于限流、生产者-消费者（缓冲区空/满）。与条件变量相比，信号量自带状态计数。

### 原子操作（Atomic）与内存屏障

- **原子操作**：如 `fetch_add`、`compare_exchange`，在单条指令层面完成「读-改-写」，不会被线程切换打断。是构建更复杂原语与无锁结构的积木。
- **内存屏障（memory barrier / fence）**：现代 CPU 与编译器会乱序执行以提升性能，但并发下会破坏「写后读」的预期顺序。屏障强制某些访存在此点之前/之后完成。常见模型：顺序一致（sequential consistency）、获取-释放（acquire-release）、宽松（relaxed）。

### 无锁编程（Lock-free）

用 CAS（compare-and-swap）循环重试来更新共享状态，避免加锁带来的阻塞与优先级反转：

```rust
// 简化示意：无锁栈的 push（实际需处理 ABA）
loop {
    let head = head_ptr.load(Relaxed);
    new_node.next = head;
    if head_ptr.compare_exchange(head, new_node, AcqRel, Relaxed).is_ok() {
        break;
    }
    // CAS 失败说明被别的线程改了，重试
}
```

- **ABA 问题**：值从 A 变 B 又变回 A，CAS 误以为没变。解决：带版本号/标记指针（如 `AtomicMarkableReference`、Hazard Pointer）。
- **RCU（Read-Copy-Update）**：读者无锁、写者复制新副本并更新指针，旧副本等所有读者退出后再回收。Linux 内核大量使用，适合读极多写极少。

### 本章主线

同步原语构成一个「工具箱」：互斥锁/自旋锁解决「排他」，读写锁优化读多写少，条件变量/信号量解决「等待条件」，原子操作与屏障是更底层的积木，无锁（CAS/RCU）则在极端性能场景下替代锁。选型的本质是**在正确性、性能、复杂度之间权衡**。

## 示例

### 示例 1：用条件变量实现生产者-消费者

```cpp
std::mutex m; std::condition_variable cv;
std::queue<int> q; const size_t CAP = 10;

void producer(int x) {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, [&]{ return q.size() < CAP; }); // 缓冲未满才生产
    q.push(x);
    cv.notify_one();
}
void consumer() {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, [&]{ return !q.empty(); });     // 缓冲非空才消费
    int x = q.front(); q.pop();
    cv.notify_one();
}
```

注意 `wait` 用 lambda 复查条件，防止虚假唤醒。

### 示例 2：用原子实现无锁计数器

```rust
use std::sync::atomic::{AtomicU64, Ordering};
let counter = AtomicU64::new(0);
counter.fetch_add(1, Ordering::Relaxed); // 单条原子指令，无需加锁
```

`fetch_add` 是原子的，多核并发自增不会丢失更新；`Relaxed` 表示不约束其他内存的可见顺序（本例足够）。

### 示例 3：死锁的四个必要条件

1. **互斥**：资源不可共享。
2. **占有并等待**：持有一个资源同时等待另一个。
3. **不可剥夺**：已分配资源不能被强制收回。
4. **循环等待**：存在线程环，每人持环中下一人的所需资源。

破坏任一条件即可避免死锁——例如「按固定全局顺序加锁」破坏循环等待。

## 易错点

- **条件变量不在循环里复查**：虚假唤醒会让线程在条件未满足时继续执行，必须用 `while`/`wait(pred)` 复查。
- **在持有自旋锁时睡眠**：自旋锁忙等期间若发生调度/睡眠，会导致长时间卡死；自旋锁临界区必须极短且不可阻塞。
- **以为原子操作自带全局顺序**：`Relaxed` 只保原子性不保顺序，需要可见性时用 `Acquire/Release`。
- **CAS 循环忽略 ABA**：无锁结构若只用裸指针/值，可能踩 ABA；务必加版本或标记。
- **把互斥锁当信号量滥用**：二值信号量能当锁，但锁有「谁加谁解」的所有权语义，更易排查。

## 小结

并发同步原语是一个分层工具箱：互斥锁与自旋锁做排他访问，读写锁优化读多写少，条件变量与信号量管理「等待-通知」，原子操作与内存屏障是更底层的正确性基石，无锁（CAS/RCU）在极限性能场景替代锁。选型的核心是在**正确性、性能与复杂度**之间权衡，并始终警惕死锁、虚假唤醒、内存可见性与 ABA 等经典陷阱。
