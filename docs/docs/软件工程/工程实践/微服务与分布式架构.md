## 核心概念

微服务不是「更先进的架构」，而是**用运维复杂度换取组织可扩展性**的一笔交易。拆分之后，原本一次函数调用变成了一次可能失败、可能超时、可能乱序的网络调用；原本一次数据库事务变成了需要 Saga 或最终一致性来兜底的分布式问题。它值得做的前提是团队规模和迭代速度已经被单体架构卡住——而不是因为它时髦。

当单体应用变得难以维护，可将其拆分为一组松耦合、独立部署的服务。代价是分布式固有的复杂性。

## 单体 vs 微服务

- 单体：简单、易调试，但随规模增长编译慢、耦合重。
- 微服务：独立开发部署、技术异构，但需面对网络、一致性与运维复杂度。

## 服务拆分

按业务域（而非技术层）拆分，遵循「高内聚、低耦合」。每个服务自拥数据库，避免共享库强耦合。

## 通信方式

| 方式 | 特点 | 适用 |
| --- | --- | --- |
| REST/HTTP | 简单、易调试 | 对外/低频调用 |
| gRPC | 高效、强类型 | 内部高频调用 |
| 消息队列 | 异步、解耦 | 事件驱动/削峰 |

### gRPC 示例

用 proto 定义强类型契约，生成代码即文档，比手写 JSON 串更不易错位：

```protobuf
service OrderService {
  rpc CreateOrder(CreateOrderReq) returns (CreateOrderResp);
}

message CreateOrderReq {
  string user_id = 1;
  repeated OrderItem items = 2;
}
```

## 服务发现与网关

- 服务发现：新实例注册、调用方动态查地址（如 Consul、etcd）。
- API 网关：统一入口，负责路由、鉴权、限流、灰度。

## 数据一致性

分布式事务难做，常用最终一致：

- **Saga**：把长事务拆为一系列本地事务，失败时反向补偿。
- **消息队列 + 幂等**：通过事件异步同步，消费者保证幂等。

### Saga 示例（下单）

```text
1. 创建订单(本地) → 成功
2. 扣库存(本地)   → 成功
3. 扣钱包(本地)   → 失败
   → 补偿: 回滚库存
   → 补偿: 取消订单
```

每一步都有对应的补偿动作，任一步失败就按相反顺序回滚，保证最终一致。

## 可观测性

- 日志集中采集（ELK/Loki）。
- 指标监控与告警（Prometheus/Grafana）。
- 链路追踪（OpenTelemetry）定位跨服务慢调用。

:::warning
不要为了微服务而微服务。团队规模与系统复杂度没到阈值前，单体加清晰模块边界往往更高效。
:::

## 易错点

- **共享数据库/强耦合库**：服务间直接连同一张表或 import 对方内部模块，拆了等于没拆。每个服务自拥数据。
- **忽视网络不可靠**：把远程调用当本地函数用，不处理超时/重试/熔断，一次抖动拖垮全链。
- **误用分布式事务**：强一致两阶段提交在长链路下锁资源、性能差，多数业务用最终一致更合适。

## 练习

设计「用户下单」场景：订单、库存、支付三个服务各自独立。写出 Saga 步骤与每一步的补偿动作，并指出哪一步最该加幂等、为什么。

## 示例

把「订单服务」落成一个最小可运行的服务，它自己持有数据、独立部署，这正是微服务「自拥数据、边界清晰」的体现：

```python
# 一个最小微服务：订单服务，独立拥有自己的数据端口
from fastapi import FastAPI

app = FastAPI(title="order-service")

orders = {}

@app.post("/orders")
def create(amount: float):
    oid = len(orders) + 1
    orders[oid] = {"id": oid, "amount": amount, "status": "CREATED"}
    return orders[oid]

@app.get("/orders/{oid}")
def get(oid: int):
    return orders.get(oid, {"error": "not found"})

# 网关侧只需按服务名路由：
#   /order/*  -> order-service:8001
#   /user/*   -> user-service:8002
# 服务地址从注册中心（Consul/etcd）动态获取，而非写死 IP。
```

多个这样的服务之间通过 HTTP/gRPC 通信，由 API 网关统一入口、注册中心做服务发现，就构成了上文所述微服务架构的最小骨架。

## 小结

先把单体写好再谈拆分。拆分的收益是团队自治与独立部署，代价是网络不可靠、事务被打散、排障链路变长——三样配套能力（网关、追踪、一致性方案）缺一不可。
