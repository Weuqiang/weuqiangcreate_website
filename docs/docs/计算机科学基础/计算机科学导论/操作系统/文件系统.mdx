# 文件系统

磁盘本质上只是「一大堆编了号的扇区」，它不知道什么是文件、什么是目录。**文件系统**就是操作系统架在裸磁盘之上的一层抽象：把线性的块地址组织成有名字、有层级、有权限的文件树。这与操作系统的另外两个核心抽象一脉相承——进程抽象 CPU、虚拟内存抽象 RAM、文件系统抽象磁盘。

## 学习目标

- 说清 inode 与目录项（dentry）的分工，理解「文件名不属于文件」这个反直觉的事实。
- 解释硬链接与软链接的本质区别，并预测各种操作后的行为。
- 说清三种块分配策略的取舍，以及多级索引如何支持大文件。
- 理解页缓存、`write` 与 `fsync` 的关系，以及日志（journal）如何保证崩溃一致性。

## 前置知识

在阅读下面的内容前，建议先掌握：

- 已了解 [内存管理](/docs/计算机科学基础/计算机科学导论/操作系统/内存管理) 中的页缓存与块设备概念。
- 知道磁盘是「按块读写」的持久存储，与易失内存相对。
- 用过任何操作系统的文件管理器即可，不要求底层知识。

## 核心概念
### 三层抽象

```text
应用    open("/home/a.txt") → 文件描述符 fd
  ↓
逻辑层  路径解析 → 目录项(dentry) → inode 编号
  ↓
inode   元数据 + 数据块指针（不含文件名！）
  ↓
块层    逻辑块号 → 物理扇区号
  ↓
硬件    磁盘/SSD
```

### inode：文件的真正身份证

一个文件由两部分构成，它们**分开存储**：

- **inode（索引节点）**：存储文件的**全部元数据**——大小、权限、属主、三个时间戳、链接计数，以及**指向数据块的指针**。每个 inode 有唯一编号。
- **目录项（dentry）**：存在目录文件里的一条 `(文件名 → inode 编号)` 映射。

**inode 里没有文件名**。这是文件系统最反直觉、也最重要的设计。目录本身就是一个特殊的文件，它的内容是一张「文件名 → inode 号」的表：

```text
目录 /home 的内容：
+----------+-----------+
| 文件名   | inode 号  |
+----------+-----------+
| .        |  128      |   ← 自己
| ..       |  2        |   ← 父目录
| a.txt    |  1024     |
| notes    |  1025     |
+----------+-----------+

inode 1024:
  类型: 普通文件   大小: 4096
  权限: rw-r--r--  属主: user
  链接计数: 2
  数据块指针: [块#500, 块#501, ...]
```

这个设计直接解释了几件事：

- **为什么删除文件叫 `unlink`？** 因为它删的是目录里的那条映射，而不是文件本身。只有当 inode 的**链接计数降到 0 且没有进程打开它**时，数据块才真正被回收。
- **为什么重命名/移动同分区文件那么快？** 只改目录项，不动数据。移动 10GB 的文件到同分区的另一个目录，是毫秒级操作。
- **为什么正在运行的程序可以被删除？** 因为进程持有打开的文件描述符，链接计数虽然到 0，但引用还在，数据要等进程退出才释放。这也是「删了日志文件但磁盘空间没释放」的经典原因——必须重启写日志的进程。

### 硬链接 vs 软链接

| 维度 | 硬链接（hard link） | 软链接 / 符号链接（symlink） |
|---|---|---|
| 本质 | 同一 inode 的另一个名字 | 一个**独立文件**，内容是目标路径字符串 |
| 有自己的 inode 吗 | ❌ 共享同一个 | ✅ 有独立 inode |
| 能跨文件系统吗 | ❌ 不能（inode 号只在本分区唯一） | ✅ 能 |
| 能指向目录吗 | ❌ 通常禁止（会造成环） | ✅ 能 |
| 删原文件后 | 仍可访问（链接计数减 1） | **失效**（悬空链接） |
| 修改其一 | 另一个同步变化（本就是一个文件） | 同步（软链接只是指路） |

一句话记：**硬链接是「同一个人的另一个称呼」，软链接是「写着地址的便利贴」**。

### 块分配策略

文件的数据要放在磁盘块里，怎么记录「哪些块属于这个文件」？

| 策略 | 做法 | 优点 | 缺点 | 使用者 |
|---|---|---|---|---|
| **连续分配** | 记起始块 + 长度 | 顺序读最快，元数据极小 | 外部碎片严重，文件无法增长 | CD-ROM、ISO |
| **链式分配** | 每块存下一块的指针 | 无外部碎片，易增长 | **随机访问是 $O(n)$**，一个坏块断全链 | 早期 FAT |
| **索引分配** | inode 里存一张块指针表 | 随机访问 $O(1)$ | 小文件也要占一个索引块 | ext2/3/4、UFS |
| **extent（区段）** | 记「起始块 + 连续长度」的区段列表 | 大文件元数据极小 | 实现复杂 | ext4、XFS、NTFS |

**多级索引**是索引分配处理大文件的关键技巧。以经典 ext2 为例，inode 里有 15 个指针：

| 指针 | 类型 | 可寻址数据量（块大小 4KB，指针 4 字节） |
|---|---|---|
| 0～11 | 直接指针 | $12 \times 4\text{KB} = 48$ KB |
| 12 | 一级间接 | $1024 \times 4\text{KB} = 4$ MB |
| 13 | 二级间接 | $1024^2 \times 4\text{KB} = 4$ GB |
| 14 | 三级间接 | $1024^3 \times 4\text{KB} = 4$ TB |

**手算说明**：4KB 的块能装 $4096 / 4 = 1024$ 个指针。一级间接指向一个「全是指针的块」，故能多寻址 1024 个数据块。

这个设计的精妙之处在于**小文件快、大文件也能存**：绝大多数文件小于 48KB，只用直接指针，一次 IO 就能拿到所有块地址；而大文件虽然要多几次间接跳转，但占比很小。这是典型的**为常见情况优化**。

### 页缓存与持久化：write 并不等于写入磁盘

调用 `write()` 返回成功时，数据通常**只在内存的页缓存里**，还没落盘。操作系统会延迟批量刷盘以提升性能。

```text
应用 write()  →  页缓存（内存，脏页）  →  [延迟] → 磁盘
                       ↑
                  此时断电 = 数据丢失
```

想确保数据真的落盘，必须显式调用 `fsync(fd)`。这就是为什么数据库、日志系统在关键提交点都会 fsync——性能换可靠性。

**崩溃一致性问题**：一次「创建文件」涉及多个磁盘写（分配 inode、更新位图、写目录项、写数据块）。如果在中间断电，文件系统就处于不一致状态（比如 inode 已分配但目录项没写，块被永久占用却无人引用）。

两种解决方案：

- **日志（Journaling）**：先把「我要做什么」写进日志区并 fsync，再执行实际修改，完成后清除日志。崩溃后重放日志即可。ext3/ext4、NTFS、XFS 都用这个方案。ext4 提供三种模式：`journal`（数据和元数据都记日志，最安全最慢）、`ordered`（默认，只记元数据但保证数据先于元数据落盘）、`writeback`（只记元数据，最快最不安全）。
- **写时复制（Copy-on-Write）**：永不原地修改，总是写到新块，最后原子地切换根指针。ZFS、Btrfs、APFS 采用此方案，天然支持快照。

### 常见文件系统对比

| 文件系统 | 平台 | 特点 | 单文件上限 |
|---|---|---|---|
| FAT32 | 通用（U 盘） | 简单、兼容性最好 | **4 GB** |
| exFAT | 通用（大容量 U 盘） | 突破 4GB 限制，无日志 | 16 EB |
| NTFS | Windows | 日志、权限 ACL、压缩、加密 | 16 TB+ |
| ext4 | Linux | 日志 + extent，最通用 | 16 TB |
| XFS | Linux（服务器） | 大文件与高并发优异 | 8 EB |
| Btrfs / ZFS | Linux / Unix | CoW、快照、校验和、软 RAID | 16 EB |
| APFS | macOS | CoW、快照、为 SSD 优化 | 8 EB |

## 最小示例

下面这段代码用 Python 观察 inode、硬链接、软链接的真实行为：

```python
import os
import tempfile

d = tempfile.mkdtemp()
original = os.path.join(d, "original.txt")
hard = os.path.join(d, "hard_link.txt")
soft = os.path.join(d, "soft_link.txt")

# ---- 1. 创建文件，查看 inode ----
with open(original, "w", encoding="utf-8") as f:
    f.write("hello filesystem\n")

st = os.stat(original)
print(f"inode = {st.st_ino}, 大小 = {st.st_size}, 链接计数 = {st.st_nlink}")
# inode = 1234567, 大小 = 17, 链接计数 = 1

# ---- 2. 硬链接：共享同一个 inode ----
os.link(original, hard)
print(f"原文件 inode = {os.stat(original).st_ino}")
print(f"硬链接 inode = {os.stat(hard).st_ino}")        # 完全相同！
print(f"链接计数 = {os.stat(original).st_nlink}")       # 2

# ---- 3. 软链接：独立 inode，内容是路径字符串 ----
os.symlink(original, soft)
print(f"软链接自身 inode = {os.lstat(soft).st_ino}")     # lstat 不跟随链接，不同
print(f"软链接指向 inode = {os.stat(soft).st_ino}")      # stat 跟随链接，相同
print(f"软链接内容 = {os.readlink(soft)}")               # 就是目标路径字符串

# ---- 4. 删除原文件：硬链接存活，软链接失效 ----
os.unlink(original)                                      # 注意函数名就叫 unlink
print(f"硬链接还能读吗: {open(hard).read().strip()!r}")  # 'hello filesystem'
print(f"硬链接计数 = {os.stat(hard).st_nlink}")           # 从 2 降到 1
print(f"软链接是否有效: {os.path.exists(soft)}")          # False —— 悬空
print(f"软链接自身还在吗: {os.path.lexists(soft)}")       # True —— 文件还在，只是指向空

# ---- 5. 目录也是文件：读取目录项 ----
print(f"目录内容 = {sorted(os.listdir(d))}")
# ['hard_link.txt', 'soft_link.txt']

# ---- 6. 持久化：write 与 fsync ----
p = os.path.join(d, "durable.txt")
with open(p, "w") as f:
    f.write("important data")
    f.flush()          # ① 把 Python 缓冲区刷到操作系统
    os.fsync(f.fileno())  # ② 命令操作系统把页缓存刷到物理磁盘
print("已确保落盘")

# ---- 7. 元数据一览 ----
st = os.stat(hard)
print(f"权限 = {oct(st.st_mode)[-3:]}, 块数 = {st.st_blocks}, 修改时间 = {int(st.st_mtime)}")
```

**关键观察点**：

| 观察 | 结论 |
|---|---|
| `os.stat(original).st_ino == os.stat(hard).st_ino` | 硬链接就是同一个文件 |
| `os.lstat(soft).st_ino != os.stat(soft).st_ino` | 软链接是独立的文件 |
| 删原文件后硬链接仍可读 | 数据块由链接计数保护 |
| 删原文件后 `exists(soft)` 为 False，`lexists(soft)` 为 True | 软链接自身存在但目标不存在 |

`flush()` 与 `fsync()` 的两级缓冲是最容易被忽略的一点：`flush()` 只把数据从**语言运行时的缓冲区**送到操作系统，`fsync()` 才让操作系统把**页缓存**送到磁盘。少任何一步，断电都会丢数据。

## 易错点

1. **以为 `write()` 返回成功就安全了。** 数据可能还在页缓存里。关键数据必须 `fsync`。数据库的每一次事务提交都伴随 fsync，这是它比直接写文件慢的主要原因之一。

2. **删了大日志文件但磁盘空间没释放。** 因为还有进程持有该文件的描述符，链接计数虽为 0 但引用未断。用 `lsof | grep deleted` 定位，然后重启进程或用 `truncate -s 0` 清空而非删除。

3. **硬链接跨分区。** 硬链接依赖 inode 号，而 inode 号只在单个文件系统内唯一，所以跨分区必然失败。需要跨分区时用软链接。

4. **删除软链接时误加斜杠。** `rm mylink/` 可能删掉目标目录的内容而不是链接本身。删软链接就写 `rm mylink`，不加尾部斜杠。

5. **inode 耗尽但磁盘还有空间。** inode 数量在格式化时就固定了。海量小文件（如缓存目录）会先耗尽 inode，此时 `df -h` 显示有空间，创建文件却报 `No space left on device`。用 `df -i` 才能看出真相。

6. **在 FAT32 上存超过 4GB 的文件。** 这是格式限制，不是软件 bug。大文件要用 exFAT 或 NTFS。

7. **混淆文件大小与占用空间。** `st_size` 是逻辑大小，`st_blocks × 512` 是实际占用。小文件因块对齐会占用整块（内部碎片）；稀疏文件则相反，逻辑大小远大于实际占用。

8. **忽视文件名编码与大小写敏感性。** Linux 的 ext4 大小写敏感，Windows 的 NTFS 和 macOS 的 APFS 默认不敏感。跨平台项目里 `README.md` 和 `readme.md` 可能是同一个文件，也可能是两个——这是 Git 仓库跨平台协作的经典坑。

## 练习

1. 运行上面的代码，把输出中的 inode 号记录下来，验证硬链接与原文件确实一致、软链接确实不同。
2. 用 `os.link` 创建 3 个硬链接，观察 `st_nlink` 的变化；逐个删除，验证只有计数归零后数据才真正消失（提示：删除前先记录 inode，删除后用 `os.stat` 会抛 `FileNotFoundError`）。
3. 创建一个**稀疏文件**：`f.seek(10**9); f.write(b"x")`，然后对比 `st_size` 与 `st_blocks * 512`。解释为什么两者差距巨大。
4. 手算：块大小 4KB、指针 4 字节的 ext2 文件系统，如果块大小改为 8KB，三级间接能寻址多大的文件？（提示：每块指针数变成 2048。）
5. 在 Linux 上执行 `df -i` 和 `df -h`，对比 inode 使用率与空间使用率。思考什么样的工作负载会先耗尽 inode。
6. 写一段代码测量 `fsync` 的开销：分别做 1000 次「写入 + fsync」和 1000 次「只写入，最后 fsync 一次」，对比耗时。这个差距解释了为什么数据库要做「组提交」。
7. 阅读 ext4 的三种日志模式（`data=journal` / `ordered` / `writeback`），说明各自在崩溃后可能出现什么样的数据状态。

## 小结

文件系统的核心设计只有一句话：**用 inode 保存「文件是什么」，用目录项保存「文件叫什么」，两者分离**。这一分离带来了硬链接、快速重命名、以及「删除正在使用的文件」等一系列行为，理解它就理解了 Unix 文件模型的一半。另一半是**性能与可靠性的权衡**：多级索引为小文件优化的同时兼容大文件，页缓存用延迟写换吞吐量，日志或写时复制用额外写入换崩溃一致性。日常运维中最常撞上的三个坑——*删文件不释放空间、inode 耗尽、write 后断电丢数据*——全都能从这些原理直接推导出来。
