全球有无数种项目管控的方案，PMBOK将项目管理的知识、过程和步骤整理为了10大知识域、5大过程组、49个步骤。项目进入标准化管理时代。

其中10大知识域我将其分为四个部分。

核心统领：<HoverText text="整合" explanation="项目整合管理包括为识别、定义、组合、统一和协调项目管理过程组的各个过程和活动而开展的过程与活动，是项目管理的核心。" />

三重约束：<HoverText text="范围" explanation="项目范围管理包括确保项目做且只做所需的全部工作以成功完成项目的各个过程，涉及需求收集、范围定义、WBS创建等。" />、<HoverText text="进度" explanation="项目进度管理包括为管理项目按时完成所需的各个过程，涉及活动定义、排序、资源估算、持续时间估算、进度制定和进度控制。" />、<HoverText text="成本" explanation="项目成本管理包括为使项目在批准的预算内完成而对成本进行规划、估算、预算、融资、筹资、管理和控制的各个过程。" />

执行保障：<HoverText text="质量" explanation="项目质量管理包括把组织的质量政策应用于规划、管理、控制项目和产品质量要求，以满足干系人期望的各个过程。" />、<HoverText text="资源" explanation="项目资源管理包括识别、获取和管理所需资源以成功完成项目的各个过程，包括人力资源、设备、材料等的管理。" />、<HoverText text="沟通" explanation="项目沟通管理包括通过开发工件，以及执行用于有效交换信息的各种活动，来确保项目及其干系人的信息需求得以满足的各个过程。" />、<HoverText text="风险" explanation="项目风险管理包括规划风险管理、识别风险、开展风险分析、规划风险应对、实施风险应对和监督风险的各个过程，目的是提高积极风险的概率和影响，降低消极风险的概率和影响。" />

项目边界：<HoverText text="采购" explanation="项目采购管理包括从项目团队外部采购或获取所需产品、服务或成果的各个过程，涉及合同管理和变更控制。" />、<HoverText text="干系人" explanation="干系人是能影响项目决策、活动或结果的个人、群体或组织，以及会受项目决策、活动或结果影响，或自认为会受到影响的个人、群体或组织。" />

:::info
小型项目只有核心统领和三重约束。

中型项目执行保障至关重要。

大型项目的项目边界也决定项目成败。

项目的资源中的人力资源更多指参与项目的人。干系人**在此基础上**，囊括了不参与项目但能影响项目的人，例如政府监管部门不参与项目，但是属于项目干系人。
:::

5大过程组按照项目进度划分为：<HoverText text="启动" explanation="启动过程组包括定义一个新项目或现有项目的一个新阶段、获得授权以开始该项目或阶段的一组过程。" />、<HoverText text="规划" explanation="规划过程组包括明确项目范围、细化目标，为实现目标而制定行动方案的一组过程，是项目工作量最大的阶段。" />、<HoverText text="执行" explanation="执行过程组包括完成项目管理计划中确定的工作，以满足项目要求的一组过程，涉及协调人员和资源，整合并实施活动。" />、<HoverText text="监控" explanation="监控过程组包括跟踪、审查和调整项目进展与绩效，识别必要的计划变更并启动相应变更的一组过程。" />、<HoverText text="收尾" explanation="收尾过程组包括为完结所有过程组的所有活动，正式结束项目、阶段或合同而实施的一组过程。" />。

:::info
没有人在完美的流程下做项目，项目快结束还在修订启动阶段计划书的情况也屡见不鲜。

因此这5个流程不是严格的你方唱罢我登场，而是同时存在在项目始终的。

收尾也可能在开头就有，只不过工作量大部分的时候是在最后。

譬如我做项目第一个问题就是：项目收尾时，我需要给你们什么样的资料？
:::

## 项目基本要素

### 项目基础

项目是为<Highlight>独特</Highlight>的<HoverText text="产品" explanation="一个新开发的软件系统" />、<HoverText text="服务" explanation="一次企业内部培训服务"/>或<HoverText text="成果" explanation="一次荒漠土地绿化项目"/>而进行的 <Highlight>临时性</Highlight>工作。

项目启动背景：<HoverText text="法律要求" explanation="例如法律规定即日起医院需要有在线挂号系统" />、干系人需求、<HoverText text="业务或技术战略" explanation="例如公司战略是技术自主可控，启动鸿蒙项目" />、创造、改进产品。

项目驱动变更：改变现状

项目创造业务价值：有形或者无形

### 项目管理的重要性

| 有效项目管理 | 管理不善|
| ---------- | ---------- |
| 达成业务目标 | 项目无法达成业务目标 |
| 干系人满意 | 干系人不满 |
| 项目范围可控 | 项目范围失控 ： 超时、超支、质量不达标、返工、组织声誉受损|

### 项目成果标准

成功的项目结果 != 项目成功

成果性目标（即项目交付的最终产品、服务或成果）和管理性目标（范围、时间、质量、成本）都要达成。

:::note
项目不成功的例如：<HoverText text="范围不达标" explanation="项目实际交付的内容少于或不符合最初约定或批准的范围" />，超时完成、超成本完成、质量不达标（装修时墙面平整度不佳）。
:::

### 项目、项目集、项目组合和运营

游乐场中，每个游乐设施建设都是一个项目。建成后交由运营部门管理来创造价值。

项目集：项目集的项目是**集成关联**的，资源共享。
:::note
例如公司同时承接了某政府的普查工作（事多钱少）、设备采购（事少钱多）。

正常公司是不会接普查工作这样接近于赔钱的项目，但是为了获取设备采购项目，公司会接下普查工作。

此时公司做预算时，会计算两个项目合起来的盈利目标，预算共享。此时两个项目就构成了一个项目集。
:::

项目组合：为了是实现组合**组织战略**，可以包含多个项目集、项目、运营。不一定是相互关联的。主要是为了确定同一组织下项目的优先级。

:::note
例如公司通常会有：政府事业部、商业事业部。

商业事业部的内很多的项目并不都是相互关联的，但是符合公司战略划分，因此可以看作一个项目组合。
:::


### 项目内外部运行环节

| 组织过程资产 | 组织**内部事业**环境| 组织**外部事业**环境|
| ---------- | ---------- | ---------- |
| 自己公司的过程资产 | 公司的影响 | 社会、政府的影响|
| 过程资产：工具、方法、模板、框架| 公司企业文化、结构和治理 | 市场条件|
| 治理文件：政策和流程文件|员工能力 |社会文化的影响 | 
| **数据资产**：各种数据库(企业自己建设的) | 信息技术软件 |监管环境 | 
| 知识产权 |设施资源的地理分布情况 |商业数据库（购买来的） |
| 安保和安全 |基础设置：办公场地 | 学术研究、行业标准、财务要求|

:::note
组织过程资产是一个受控的状态、团队可以调整改变这些过程资产。

事业环境因素往往不受控，主要来自于公司大环境、社会环境、政府环境。
:::

### 组织结构类型

组织结构决定了项目经理能调动多少资源、说话有多大分量。常见结构归为三大类，矩阵型再细分为弱、平衡、强三档。

| 组织结构 | 项目经理权力 | 资源可用性 | 预算控制方 | 项目经理角色 | 团队专职程度 |
| ---------- | ---------- | ---------- | ---------- | ---------- | ---------- |
| 职能型 | 很小或没有 | 很少 | 职能经理 | 兼职协调 | 兼职 |
| 弱矩阵 | 小 | 少 | 职能经理 | 兼职协调员或联络员 | 兼职 |
| 平衡矩阵 | 中等 | 中等 | 职能经理与项目经理共管 | 专职 | 以兼职为主 |
| 强矩阵 | 较大 | 较多 | 项目经理 | 专职 | 多数专职 |
| 项目型 | 很大或全权 | 很多 | 项目经理 | 专职 | 全职 |

- 职能型：按专业划分部门，人员向职能经理汇报，项目只是部门内的一项额外工作。
- 矩阵型：双重汇报线，成员既属于职能部门又属于项目团队，冲突主要来自资源争夺和考核归属。
- 项目型：团队按项目组建，资源集中、响应快，代价是项目结束后的人员安置和知识沉淀。

:::note
判断组织落在哪一档，最快的办法是问两个问题：谁签字批预算？谁决定这个人下周干什么？答案落在项目经理一侧越多，结构就越偏项目型。
:::

### 项目管理办公室（PMO）

<HoverText text="PMO" explanation="Project Management Office，项目管理办公室，是对项目进行标准化管理并促进资源、方法论、工具和技术共享的组织部门。" /> 按对项目的控制程度分为三类。

| PMO 类型 | 控制程度 | 主要做法 | 典型场景 |
| ---------- | ---------- | ---------- | ---------- |
| 支持型 | 低 | 提供模板、最佳实践、培训和信息库，充当项目资源库 | 项目自主性强、组织成熟度较低 |
| 控制型 | 中 | 要求项目采用统一方法论、模板与治理框架，并做合规检查 | 需要统一口径、审计要求较严 |
| 指令型 | 高 | 直接接管项目，项目经理由 PMO 指派并向 PMO 汇报 | 战略级项目、组织要求强管控 |

PMO 的常见职能：
- 标准制定：统一方法论、流程、模板和绩效指标
- 资源协调：跨项目调配人力与设备，裁决优先级冲突
- 知识沉淀：归集经验教训、历史数据和组织过程资产
- 监督汇报：汇总多项目进度与绩效，为管理层提供决策依据

:::tip
PMO 不是「多加一层审批」。它存在的意义是让下一个项目不必重新踩一遍坑——如果只产出报表而不沉淀资产，它就退化成了汇报中转站。
:::

### 项目管理和产品管理

| 对比维度 | 项目管理 | 产品管理 |
| ---------- | ---------- | ---------- |
| 性质 | 临时性，有明确起止 | 持续性，贯穿产品生命周期 |
| 目标 | 在约束内交付既定成果 | 持续提升产品的市场价值 |
| 成功标准 | 范围、进度、成本、质量达标 | 用户规模、营收、留存等业务指标 |
| 主要关注 | 交付物与过程 | 需求优先级与商业回报 |
| 结束条件 | 验收移交后关闭 | 产品退市才结束 |

两者的交集在于：产品的每一次重大版本、每一次能力建设，通常都以项目的形式立项和交付。产品侧回答「做什么、为什么做」，项目侧回答「怎么做、何时做完」。

:::note
在敏捷与持续交付的语境下，这条界限明显模糊：迭代持续滚动，没有清晰的收尾节点，团队长期稳定存在，产品负责人同时承担排优先级和把控交付节奏的职责。此时更贴切的说法不是「项目结束了」，而是「这个产品增量上线了」。
:::

## 项目经理的角色

项目经理由执行组织委派，领导团队实现项目目标。他不必是技术最强的人，但必须是对项目结果负总责的人。

职责范围：
- 对上：向发起人和管理层汇报进展、暴露风险、申请资源与决策
- 对内：组建并建设团队，分配任务，处理冲突，维持士气
- 对外：识别并管理干系人期望，协调供应商与外部依赖
- 对事：制定并维护项目管理计划，跟踪偏差，管理变更

项目经理所需的能力可归为三类：

| 能力 | 含义 | 具体表现 |
| ---------- | ---------- | ---------- |
| 技术项目管理 | 项目管理专业本身的知识与技能 | 熟悉方法论，会做 WBS 与进度网络，会算成本偏差，会开有效的评审会 |
| 领导力 | 指导团队达成目标的软技能 | 愿景牵引、沟通谈判、激励授权、冲突处理 |
| 战略与商务管理 | 理解组织所处环境并作出有利决策 | 懂业务模式与财务口径，能把项目目标翻译成业务价值 |

:::note
越是小项目越依赖技术项目管理能力；项目和组织越大，领导力与战略商务能力的权重越高。
:::

与其他角色的关系：

| 角色 | 关系定位 | 常见摩擦点 |
| ---------- | ---------- | ---------- |
| 发起人 | 提供资金、授权和政治支持，签发项目章程，裁决重大变更 | 目标漂移、承诺的资源不到位 |
| 职能经理 | 掌握人员归属与专业标准，是项目资源的实际供给方 | 人员被抽调、绩效考核归属不清 |
| 运营经理 | 接收项目成果并投入日常运营 | 交付标准与运维要求不一致 |
| 团队成员 | 执行主体，在矩阵型组织中双线汇报 | 多项目并行导致投入被稀释 |

:::tip
项目经理的权力大多来自影响力而非职权，在矩阵型组织里尤其如此。把发起人用好——很多靠职权解不开的资源死结，一次发起人层面的沟通就能推动。
:::

## 价值驱动的项目管理知识体系

### 项目生命周期结构特征

项目的生命周期常见划分：
- 启动项目 输出——> 项目章程
- 组织与准备 输出——> 项目管理计划
- 执行工作 输出——> 验收交付成果
- 结束项目 输出——> 存档文档资料

项目生命周期是产品的一部分。
:::note
一个产品启动阶段是项目，V2版本升级是另一个项目。
:::

项目前期：
- 干系人影响、风险与不确定较大
- 变更的代价较小

项目后期：
- 干系人影响、风险与不确定较小
- 变更的代价较大


### 项目生命周期类型

在上述结构特征之上，按需求确定度和交付节奏的不同，生命周期分为五类。

| 类型 | 需求确定度 | 交付方式 | 变更代价 | 适用场景 |
| ---------- | ---------- | ---------- | ---------- | ---------- |
| 预测型（瀑布） | 高，前期即可冻结 | 一次性整体交付 | 高 | 需求与技术都成熟，如土建、标准化系统集成 |
| 迭代型 | 中，方案需要试错 | 反复打磨同一成果，逐步逼近正确 | 中 | 需求清楚但实现方案不确定，如算法调优、交互设计 |
| 增量型 | 中，成果可拆分 | 分批交付可用的部分成果 | 中 | 用户希望尽早用上一部分功能 |
| 适应型（敏捷） | 低，边做边明确 | 固定短周期迭代，持续交付增量 | 低 | 需求多变、市场不确定，如互联网产品 |
| 混合型 | 各部分不一致 | 不同组成部分采用不同节奏 | 视组成而定 | 大型项目中硬件预测型、软件适应型并存 |

- 迭代与增量的区别：迭代是「改得更好」，增量是「做得更多」，敏捷通常是二者叠加。
- 选型的第一判据是需求确定度，第二判据是变更代价与交付频率的期望。

:::note
不存在放之四海皆准的生命周期。需求越不确定、试错成本越低，就越应该往适应型靠；反之合规约束强、返工代价高的项目，预测型仍然是更负责任的选择。
:::

### 项目管理过程组

| 过程组 | 目标 | 关键产出 |
| ---------- | ---------- | ---------- |
| 启动 | 定义新项目或新阶段，获得开工授权 | 项目章程、干系人登记册 |
| 规划 | 明确范围、细化目标，制定实现目标的行动方案 | 项目管理计划及各子计划，范围、进度、成本三大基准 |
| 执行 | 按计划完成工作，协调人员与资源 | 可交付成果、工作绩效数据、问题日志 |
| 监控 | 跟踪、审查并调整进展与绩效，识别并处理偏差 | 工作绩效报告、变更请求、批准的变更 |
| 收尾 | 正式结束项目、阶段或合同 | 成果移交、经验教训总结、项目文件归档 |

- 规划的过程数量最多（49 个过程中占 24 个），因为绝大部分不确定性要在这里被消化。
- 执行消耗的成本与人力最多，监控贯穿始终，与执行构成反馈闭环。
- 收尾只有 1 个过程，却最常被草草了事，结果是资产无人归档、经验无人复用。

:::note
过程组不等于生命周期阶段。生命周期阶段是按时间先后串联的项目划分，过程组则是按性质归类的过程集合——同一个阶段内部，五个过程组的活动都可能同时发生。
:::

### 项目管理五大过程组之间的关系

过程组并不像项目阶段那样依次开展的顺序关系。

各个过程组是一种交叠关系。只是随着项目推进，特定节点占比增多减少。

:::note
这是高度符合真实项目的实际情况的。

有时候你项目快结束了，还在补启动阶段的资料。

有时你项目刚启动，你先要思考最终的验收材料如何准备。
:::
