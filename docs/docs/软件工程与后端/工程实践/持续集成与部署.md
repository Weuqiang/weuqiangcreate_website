CI/CD 把「构建、测试、部署」自动化，让代码改动能快速、可靠地交付到生产。

## CI 与 CD 的区别

- **CI（持续集成）**：开发者频繁把代码合入主干，每次合入都自动构建并运行测试，尽早发现集成问题。
- **CD（持续交付 / 持续部署）**：在 CI 之后自动把通过测试的产物打包并发布到预发或生产。持续交付需人工点一下发布；持续部署则全自动。

## 一条典型流水线

1. 触发：push 或 PR。
2. 安装依赖并缓存。
3. 静态检查（lint）与单元测试。
4. 构建镜像 / 打包产物。
5. 部署到预发环境，跑集成测试。
6. 人工审批或自动发布到生产。

## GitHub Actions 示例

```yaml
name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest -q
      - run: docker build -t app:ci .
```

## 部署策略

| 策略 | 思路 | 优点 | 风险 |
| --- | --- | --- | --- |
| 蓝绿 | 两套环境，切流量 | 秒级回滚 | 资源翻倍 |
| 金丝雀 | 先放少量流量 | 影响面小 | 需流量路由 |
| 滚动 | 逐批替换实例 | 资源友好 | 新旧并存期长 |

## 质量门禁

在流水线中设置硬性门槛：测试覆盖率不低于阈值、禁止高危漏洞、构建零警告。不达标则阻断合并。

## 密钥与配置管理

流水线要连数据库、推镜像、调第三方 API，绕不开凭据。**唯一的底线：任何密钥都不能出现在仓库里**——不写进 YAML、不写进 Dockerfile、不写进代码注释。Git 历史是永久的，提交过一次就等于泄露，改回来也没用，只能去轮换密钥。

正确做法是把密钥放进 CI 平台的加密存储，运行时以环境变量注入：

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production        # 绑定环境，可配审批人与专属密钥
    steps:
      - uses: actions/checkout@v4

      - name: 登录镜像仓库
        # secrets 在日志里会被自动打码成 ***
        run: echo "${{ secrets.REGISTRY_TOKEN }}" | docker login ghcr.io -u "${{ github.actor }}" --password-stdin

      - name: 部署
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}   # 敏感：走 secrets
          APP_ENV: production                          # 非敏感：直接写
        run: ./scripts/deploy.sh
```

几条实践准则：

- **分层存放**：仓库级 Secrets 放通用凭据，Environment Secrets 放各环境（预发/生产）专属凭据，避免测试流水线拿到生产密钥。
- **敏感与非敏感分开**：`APP_ENV`、`LOG_LEVEL` 这类配置直接明文写在 `env` 里，只有真正的凭据才占用 Secrets，否则日志全是 `***` 反而难排查。
- **最小权限 + 短时效**：给 CI 的 token 只开必要的 scope。GitHub Actions 里显式收紧默认权限，比留着全量写权限安全得多：

  ```yaml
  permissions:
    contents: read
    packages: write     # 只在需要推镜像的 job 里开
  ```

- **优先用 OIDC 免密**：对接云厂商时，用 OIDC 联合身份换取临时凭据，比在 Secrets 里长期存 AK/SK 更安全，也省去定期轮换的麻烦。
- **警惕 fork PR**：`pull_request` 事件默认拿不到 Secrets（这是保护机制）。不要为了图省事改用 `pull_request_target`，那等于把密钥暴露给任何人提交的代码。
- **别自己回显密钥**：`echo $TOKEN` 或把它拼进 URL 打印出来，打码机制可能失效。调试时只输出长度或前几位。

## 常见坑

**1. 缓存没命中，每次都从零装依赖**

流水线慢，八成是依赖装了一遍又一遍。缓存的关键是 **key 要绑定锁文件的哈希**：锁文件不变就复用，变了才重装。

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: "20"
    cache: "npm"           # 内置缓存，最省事，优先用这个

# 需要自定义时：
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements*.txt') }}
    restore-keys: |
      ${{ runner.os }}-pip-     # 前缀回退：没精确命中时先用旧缓存，再增量装
```

两个易错点：key 里漏了 `runner.os`（跨平台缓存串用），以及 key 写成固定字符串（永远命中旧缓存，依赖更新不生效）。

**2. 矩阵构建：该用不用，或者用力过猛**

要覆盖多版本、多平台时，`matrix` 能把一份配置展开成多个并行 job：

```yaml
strategy:
  fail-fast: false          # 一个组合挂了，其余继续跑完，便于一次看全问题
  matrix:
    python: ["3.10", "3.11", "3.12"]
    os: [ubuntu-latest, windows-latest]
    exclude:                # 排除没必要的组合，省额度
      - os: windows-latest
        python: "3.10"
runs-on: ${{ matrix.os }}
```

注意组合数是乘法关系，三个维度很容易炸成几十个 job，既慢又烧额度。常见折中：PR 上只跑最小矩阵（主版本 + Linux），合入主干或发版时才跑全矩阵。

**3. 产物越传越大**

`upload-artifact` 把 `node_modules` 或整个构建目录传上去，几百 MB 一次，慢且占配额。只传真正需要的东西，并设置保留期：

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: dist
    path: dist/            # 只传产物，不要 node_modules、不要 .git
    retention-days: 7      # 默认 90 天，短周期产物没必要留那么久
```

另外区分清楚：**artifact 是给人下载/跨 job 传递的产物**，**cache 是为了加速下次构建的中间物**，两者用途不同，别拿 artifact 当缓存使。

**4. 人工审批卡点设计不合理**

审批不是越多越好。加在每个环节，结果就是大家闭眼点「同意」，门禁形同虚设。合理的做法是：CI 与预发全自动，只在「进生产」这一步设一道人工确认。

```yaml
jobs:
  deploy-prod:
    needs: [test, deploy-staging]
    environment:
      name: production        # 在仓库设置里给该环境配 Required reviewers
      url: https://example.com
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/deploy.sh
```

配套要做的两件事：一是审批页面上要能看到「这次改了什么」（关联 PR、commit 范围），否则审批人无从判断；二是准备好一键回滚，让「先发再说」的成本可控——**回滚能力越强，审批就能越轻**。

:::tip
先把「能跑起来的 CI」做出来，再逐步加门禁，别一上来就追求完美流水线。
:::
