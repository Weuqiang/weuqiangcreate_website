# 前端状态管理

## 学习目标

学完本章，你应该能够：

- 区分「本地 UI 状态」与「跨组件共享状态」
- 理解 Context 解决什么、又为何不应滥用
- 对比 Redux / Zustand / Pinia 的取向
- 说清「服务端状态」为何不该混进本地状态

## 前置知识

在阅读下面的内容前，建议先掌握：

- [React 核心概念](/docs/软件工程/Web前端/框架/React核心概念)

## 核心概念

状态管理的本质是：**当状态需要被多处读写时，把它放在一个明确、可控的地方**。状态该放在哪一层，取决于「谁需要它」。

本章主线：

- 本地状态 vs 共享状态
- Context：轻量跨组件传递
- 全局 store：Redux / Zustand / Pinia
- 服务端状态：单独一类

## 本地状态 vs 共享状态

- **本地 UI 状态**：只在一个组件内用（如输入框当前值、下拉是否展开）→ 用组件自身 `useState`/`ref`，别外溢。
- **共享状态**：多个互不嵌套的组件都要读/改（如登录用户、主题、购物车）→ 需要提升到共同祖先或独立 store。

经验法则：**状态待在「需要它的最小范围」**。过早放进全局 store，会让无关组件跟着重渲染、耦合变重。

## Context：轻量跨层传递

React 的 Context 让数据「穿透中间组件」直达深层消费者，避免 props 层层透传（prop drilling）：

```jsx
const ThemeContext = createContext('light');
<ThemeContext.Provider value="dark">
  <DeepChild />
</ThemeContext.Provider>
```

但 Context 有代价：**任何 value 变化，所有消费者都重渲染**。所以它适合「低频变化」的全局量（主题、 locale），不适合高频更新的数据（如每帧变化的鼠标位置）。

## 全局 store：Redux / Zustand / Pinia

当共享状态变复杂（多模块、需可预测更新、需调试时间旅行），引入 store：

| 方案 | 取向 | 适用 |
| --- | --- | --- |
| Redux (Toolkit) | 强约定、action/reducer、可时间旅行调试 | 大型、强可预测性需求 |
| Zustand | 极简 hook 式 store、按需订阅 | 中小型、想要轻量 |
| Pinia | Vue 官方推荐、组合式、TS 友好 | Vue 项目 |

共同思想：**单一数据源 + 明确的「如何改」的规则 + 订阅式更新**。Zustand/Pinia 比 Redux 轻，是因为它们放弃了「所有变更走 action 集中登记」的强约束，换取简洁。

## 服务端状态：单独一类

从 API 拉取的数据（用户列表、订单）与普通 UI 状态**性质不同**：

- 它存在于远端、会过期、需缓存与失效
- 重复请求、竞态（后发先至）、loading/error 三态都要处理

把服务端数据塞进 Redux 本地 store 是常见反模式。更优解是**数据客户端**（React Query / SWR / Vue 的同类库）：它们专管「取数、缓存、失效、后台刷新」，本地 store 只留真正的客户端状态。

## 易错点

1. **用 Context 存高频状态**：导致大范围无意义重渲染；改用 store 的细粒度订阅。
2. **服务端数据混进本地 store**：缓存/失效/竞态全要自己写；交给数据客户端。
3. **过早全局化**：把本可局部的状态塞进 store，增加耦合与重渲染面。
4. **store 里放组件实例/DOM**：状态应可序列化，混入不可序列化对象会破坏调试与持久化。

## 小结

状态管理遵循「最小范围」原则：本地状态留组件内，跨组件低频量用 Context，复杂共享用 store（Redux/Zustand/Pinia），服务端数据交给专门的数据客户端。把「谁需要、多久变、是否来自远端」想清楚，状态架构自然清晰。

## 练习

1. 找一个你项目里「被塞进全局 store 的 API 数据」，改用 React Query/SWR 类方案，对比代码与缓存行为。
2. 用 Context 传主题、用 Zustand 存购物车，体会两者适用边界。
3. 故意把高频鼠标坐标放进 Context，用性能面板观察重渲染范围，再迁移到细粒度订阅。
