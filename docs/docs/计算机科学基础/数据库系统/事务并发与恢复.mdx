# 事务并发与恢复

前面的章节让数据库「快」：好的模型、索引、优化器。但数据库还得「**对**」——两个人同时转账不能丢钱，宕机重启不能丢已提交的数据。这就是**事务（并发控制）**与**崩溃恢复**。本章承接 [查询处理与优化](/docs/计算机科学基础/数据库系统/查询处理与优化)，把「正确性保证」这条底线讲清。

## 学习目标

- 解释 ACID 四属性分别由什么机制保证（undo log / 应用约束 / 并发控制 / redo log）。
- 列出四种隔离级别，并指出脏读、不可重复读、幻读各自在哪个级别被阻止。
- 对比两阶段锁（2PL）与多版本并发控制（MVCC）的并发思路。
- 理解 WAL（先写日志）与 ARIES 三阶段（分析/重做/撤销）如何恢复崩溃。

## 核心概念

### ACID

- **A（原子性 Atomicity）**：事务要么全做、要么全不做。靠 **undo log**——回滚时反向擦除未提交修改。
- **C（一致性 Consistency）**：数据库从一种合法状态变到另一种；主要靠应用约束 + 前三者共同维护。
- **I（隔离性 Isolation）**：并发事务互不干扰。靠**锁 / MVCC** 等并发控制。
- **D（持久性 Durability）**：一旦提交，掉电也不丢。靠 **redo log / WAL**——先落日志再改页。

### 隔离级别与异常

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| 读未提交 RU | 可能 | 可能 | 可能 |
| 读已提交 RC | 阻止 | 可能 | 可能 |
| 可重复读 RR | 阻止 | 阻止 | 可能（快照隔离下） |
| 串行化 Serializable | 阻止 | 阻止 | 阻止 |

- **脏读**：读到别的事务**未提交**的中间值（它可能回滚）。
- **不可重复读**：同一事务内两次读同一行，值变了（被别的事务**已提交修改**）。
- **幻读**：同一事务内两次范围查询，多出了「新插入的行」（像幻觉）。

注意：主流数据库（如 MySQL InnoDB 的「可重复读」、Postgres 的「快照隔离」）用 **MVCC** 实现，能挡住脏读与不可重复读，但**写偏斜（write skew）**这类异常在快照隔离下仍可能发生，需串行化或显式加锁防住。

### 并发控制：2PL 与 MVCC

- **两阶段锁（2PL）**：事务分「加锁阶段」与「解锁阶段」，且两阶段不交错。能保证冲突可串行化，但读写互相阻塞、易死锁（靠超时或检测解除）。
- **多版本并发控制（MVCC）**：每次修改生成新版本、保留旧版本；读不加锁，读「事务开始时的快照」。读写不互相阻塞，大幅提升并发。**代价**是需垃圾回收旧版本（vacuum），且写-写冲突仍要靠锁。

MVCC 是现代数据库的默认选择（Postgres、InnoDB、Oracle）：读永远不阻塞写、写不阻塞读，只有写-写冲突才需处理。

### 崩溃恢复：WAL 与 ARIES

- **WAL（Write-Ahead Logging）原则**：**先写日志、再改数据页**。这样即使改页中途掉电，重启也能从日志重做（redo）已提交事务、撤销（undo）未提交事务。
- **ARIES 算法**三阶段：
  1. **Analysis**：扫描日志，确定崩溃时哪些事务活跃、哪些页脏。
  2. **Redo**：从最后一个检查点开始重放**所有**已提交的修改（重复历史，保证持久性），不管是否真的写回磁盘。
  3. **Undo**：对未提交的事务，按日志反向回滚（保证原子性）。
- **检查点（Checkpoint）**：定期把内存脏页刷盘并记录位点，缩短恢复时需要重放的日志长度。

## 最小示例

用 Python 演示「两个并发转账若不加隔离，会丢钱（丢失更新）」，以及用「读时加锁/原子更新」避免：

```python
import threading

balance = 1000
lock = threading.Lock()

def transfer_bad(amount):
    # 非原子: 读-改-写 三步分离 -> 并发时互相覆盖
    global balance
    b = balance                 # 读
    b += amount                # 改
    balance = b                # 写 (另一起动可能已覆盖)

def transfer_safe(amount):
    # 临界区加锁, 保证读-改-写原子
    global balance
    with lock:
        balance += amount

# 100 个线程各 +1, 期望 1100
ts = [threading.Thread(target=transfer_bad, args=(1,)) for _ in range(100)]
for t in ts: t.start()
for t in ts: t.join()
print("无保护余额:", balance, "(常 < 1100, 出现丢失更新)")

balance = 1000
ts = [threading.Thread(target=transfer_safe, args=(1,)) for _ in range(100)]
for t in ts: t.start()
for t in ts: t.join()
print("加锁后余额:", balance, "(= 1100, 正确)")
```

数据库的 MVCC/2PL 就是把这种「并发正确性」系统化到存储引擎里，并加上崩溃后可恢复。

## 易错点

- **以为「可重复读」就万无一失**。快照隔离挡脏读/不可重复读，但**写偏斜、幻读**在多数实现下仍可能发生；需要严格正确时用串行化或显式 `SELECT ... FOR UPDATE`。
- **混淆脏读与不可重复读**。脏读是「读到未提交的（会回滚的）」，不可重复读是「读到别人**已提交**的修改」——隔离级别分别在不同层拦截。
- **把 MVCC 当「无锁万能」**。MVCC 让读写不阻塞，但**写-写冲突**仍需锁；且旧版本堆积要靠 vacuum/清理，忽视会导致膨胀与变慢。
- **误解 WAL 顺序**。必须先落日志再改页；若反过来，掉电时「页已改、日志没记」就会丢失或破坏已提交数据。
- **死锁只靠「不出现」**。高并发下死锁不可避免，系统必须有超时或检测-回滚机制，应用层也要准备重试。

## 练习

1. 在「读已提交」级别下，事务 T1 两次读取同一行，中间 T2 提交了该行的修改——T1 两次结果可能不同吗？这叫什么异常？哪个级别能阻止？
   *答案：可能不同，这是不可重复读；「可重复读」及以上（及 MVCC 快照）可阻止。*
2. 为什么 MVCC 下「读不阻塞写、写不阻塞读」，但写-写仍冲突？
   *提示：读走旧快照无需锁；但两个写都想改同一行时，必须串行化以保原子性与一致性，靠锁/冲突检测。*
3. 数据库崩溃重启，某已提交事务的修改还在缓冲池未写盘——ARIES 如何保证它不丢？
   *答案：WAL 已先把该修改记入(redo)日志并落盘；重启 Redo 阶段重放，将其写回，保证持久性。*

## 小结

事务靠 ACID 保证正确性：原子性由 undo log、持久性由 redo log/WAL、隔离性由锁或 MVCC、一致性由约束与前三者共同维护。隔离级别逐级阻止脏读、不可重复读、幻读，但快照隔离仍需警惕写偏斜。2PL 通过加解锁阶段保证可串行化但易阻塞，MVCC 用多版本让读写互不阻塞（写-写仍冲突）。崩溃恢复遵循 WAL「先记日志再改页」，ARIES 以分析→重做→撤销三阶段从任意崩溃点恢复。这样，从 [关系模型](/docs/计算机科学基础/数据库系统/关系模型与SQL) 到 [索引](/docs/计算机科学基础/数据库系统/存储引擎与索引)、[查询优化](/docs/计算机科学基础/数据库系统/查询处理与优化) 再到事务恢复，数据库系统的主线就完整了。
