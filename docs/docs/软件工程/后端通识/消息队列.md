## 核心概念

消息队列（MQ）是一个「**生产者把消息丢进一个中间管道，消费者按自己的节奏取走处理**」的系统。它把「调用方」和「执行方」在时间、空间、速率三个维度上解耦：调用方发完就走不必等，执行方挂了重启还能继续消费，突发流量被管道缓冲而不是瞬间压垮下游。

代价是系统多了一个需要运维的中间件，并且「消息可能丢、可能重复、可能乱序」——这些必须靠语义选择和业务幂等来兜底。

## 为什么需要消息队列

| 动机 | 说明 | 例子 |
| :--- | :--- | :--- |
| 解耦 | 服务之间不直接调用，改一方不影响另一方 | 下单后「发邮件、扣库存、记账单」各自订阅订单事件 |
| 异步 | 主流程不必等耗时操作完成 | 用户注册后立即返回，发 welcome 邮件后台慢慢发 |
| 削峰 | 突发流量先堆积在队列，下游按能力消费 | 秒杀请求洪峰被缓冲，避免直接冲垮数据库 |

:::warning MQ 不是用来「加速」的
引入 MQ 通常会增加端到端延迟（消息要落盘、要被拉取），它的价值是「平稳」而非「更快」。把同步调用盲目改成异步 MQ，可能反而让用户体验变慢，要先想清楚异步是否可接受。
:::

## 两种消息模型

- **点对点（Queue / 队列）**：一条消息只被**一个**消费者处理，适合「任务分发」——比如 10 个 worker 瓜分一池任务，互不重复。
- **发布/订阅（Topic / 主题）**：一条消息被**所有**订阅了该主题的消费者各自收到一份，适合「事件广播」——比如「订单创建」事件同时触发邮件、库存、风控。

很多系统两者融合：Kafka 的「消费组」机制下，同一组内是点对点（组内分摊），不同组之间则是发布/订阅（每组都拿到全量）。

## 投递语义

这是 MQ 设计里最容易被低估、却最关键的部分：

| 语义 | 含义 | 代价 | 典型实现 |
| :--- | :--- | :--- | :--- |
| at-most-once | 至多一次，可能丢但不重复 | 最简单、最快 | 发完即忘、不确认 |
| at-least-once | 至少一次，可能重复但不丢 | 需确认+重试 | 大多数 MQ 默认 |
| exactly-once | 恰好一次 | 最复杂（需去重/事务） | Kafka 事务 + 幂等生产者 |

:::tip 现实中的选择
绝大多数业务用 **at-least-once + 消费端幂等** 就够了：保证不丢，重复来了因为业务幂等（同一订单号只处理一次）而不出错。盲目追求 exactly-once 会把系统复杂度拉得很高，往往得不偿失。
:::

## 常见中间件对比

| 中间件 | 模型侧重 | 特点 | 适合 |
| :--- | :--- | :--- | :--- |
| RabbitMQ | 队列、灵活路由 | 协议成熟（AMQP）、路由规则强、延迟低 | 任务队列、复杂路由 |
| Kafka | 高吞吐日志流 | 分区有序、持久化、水平扩展强 | 日志、事件流、大数据管道 |
| Redis Streams | 轻量流 | 复用 Redis、部署简单、功能较基础 | 中小规模、已用 Redis 的场景 |

## 幂等、重试与死信

- **幂等**：因为 at-least-once 会重复投递，消费者必须保证「同一条消息处理多次结果一致」——常见做法是用业务唯一键（订单号、消息 ID）做去重表或 `INSERT ... ON CONFLICT`。
- **重试与死信（DLQ）**：处理失败的消息不应无限重试拖垮消费速度，应有限次重试，仍失败则转入死信队列人工排查。
- **堆积**：消费者太慢会导致消息堆积，需要监控积压量并横向扩容消费组。

## 示例

下面用 Redis Streams 实现一个最小生产者/消费者，体会「发完就走、按需消费」：

```python title="Redis Streams 最小生产者/消费者"
import redis

r = redis.Redis(host="127.0.0.1", port=6379, decode_responses=True)
STREAM = "orders"

# 生产者：把订单事件追加到流，返回消息 ID（时间戳-序号）
def produce(order_id: str, amount: float) -> str:
    return r.xadd(STREAM, {"order_id": order_id, "amount": str(amount)})

# 消费者：从组内读取新消息，处理完确认（ACK），失败可重试/进死信
def consume(group: str, consumer: str):
    # 首次需创建消费组；$ 表示从最新开始，0 表示从头
    try:
        r.xgroup_create(STREAM, group, id="0", mkstream=True)
    except redis.exceptions.ResponseError:
        pass  # 组已存在

    while True:
        # 阻塞等待新消息，'>' 表示取未投递给本组的
        resp = r.xreadgroup(group, consumer, {STREAM: ">"}, count=1, block=2000)
        if not resp:
            continue
        _stream, messages = resp[0]
        msg_id, fields = messages[0]
        try:
            handle_order(fields["order_id"], float(fields["amount"]))
            r.xack(STREAM, group, msg_id)   # 处理成功，确认
        except Exception:
            # 真实场景：有限次重试后仍失败 -> 转死信队列
            pass
```

:::info 为什么用消费组 + ACK
消费组保证「组内一条消息只被一个消费者拿到」，ACK 告诉 Redis 这条已处理完；未 ACK 的消息会在消费者掉线后被重新分配给组内其他人，从而实现「至少一次」投递。配合业务幂等，重复消费也安全。
:::

## 小结

MQ 用「中间管道」把生产者和消费者在时间、空间、速率上解耦，核心价值是解耦、异步、削峰，而非提速。点对点适合任务分发、发布/订阅适合事件广播；投递语义上 at-least-once + 消费端幂等是性价比最高的组合。选型看场景：RabbitMQ 重路由、Kafka 重吞吐、Redis Streams 轻量。上线前一定想清楚重试、死信、堆积监控与幂等。

## 易错点

- 以为 MQ 能「加速」：它增加端到端延迟，价值在平稳，异步需业务可接受。
- 忽略重复消费：默认 at-least-once 会重投，消费端不做幂等就会重复下单/重复扣款。
- 不做失败重试与死信：处理失败的msg无限重试拖垮消费速度，或静默丢失无人察觉。
- 消费速度低于生产速度却无监控：消息持续堆积，等到发现时已延迟数小时。
- 把 MQ 当数据库用：消息应有可丢失/可重放的预期，重要状态最终还是要落库。
