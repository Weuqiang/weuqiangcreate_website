## 核心概念

### 为什么需要 DDD

当业务规则复杂、领域知识密集（金融、电商、物流、医疗）时，单纯「按数据库表 CRUD」写代码会让业务规则散落各处、难以维护。DDD 主张**让代码的结构反映业务领域的结构**，由领域专家与开发共同维护一套「通用语言」。

### 战略设计：通用语言与限界上下文

- **通用语言**：开发、产品、领域专家共用同一套无歧义术语，且这些术语直接体现在代码（类名、方法名）里。需求讨论与代码不再「两张皮」。
- **限界上下文**：一个概念在不同上下文含义不同（「账户」在支付与社交中语义不同）。限界上下文明确划定每个模型的适用边界，边界内术语与模型自洽。上下文之间用**上下文映射（Context Map）** 描述关系：合作关系、防腐层（ACL）、共享内核、开放主机服务等。

### 战术设计：领域模型构件

- **实体（Entity）**：有**唯一标识**、生命周期内身份不变，即使属性变化仍是「同一个」。如 `Order(id)`。
- **值对象（Value Object）**：无标识，靠属性定义相等性，不可变。如 `Money(amount, currency)`、`Address`。可自由替换、天然线程安全。
- **聚合（Aggregate）**：一组相关对象的**一致性边界**，有一个**聚合根（Aggregate Root）**。外部只能透过根访问内部对象；对聚合的修改必须满足整体业务不变量。它是事务与并发的最小单位。
- **领域服务（Domain Service）**：当操作不属于任何实体/值对象（跨多个聚合、或无状态领域规则）时，用领域服务承载。
- **领域事件（Domain Event）**：记录「领域中已发生的事实」（如 `OrderPlaced`），用于解耦后续动作（发邮件、更新库存），是事件驱动架构的基石。
- **仓储（Repository）**：封装聚合的持久化，提供「按标识获取/保存聚合」的集合式接口，把领域层与具体数据库技术隔离。

### 与架构模式的协同

- **CQRS**：把「写模型」（领域命令，强一致性）与「读模型」（为查询优化的投影）分离，常配合事件溯源。
- **事件溯源（Event Sourcing）**：不存当前状态，而存「所有领域事件」，状态由重放事件得到，天然审计友好。
- **六边形/清晰架构**：领域层位于内核，基础设施（DB、消息、Web）通过端口/适配器在外围，符合 DDD「领域为核心」的取向。

### 本章主线

DDD 分两层：战略上用通用语言 + 限界上下文把大问题切成自洽的小模型；战术上用实体/值对象/聚合等构件把业务规则固化进代码。它把「业务复杂度」作为一等公民，是应对复杂领域、支撑可演进微服务系统的关键方法论。

## 示例

### 示例 1：聚合根保证不变量

```java
// 订单是聚合根，订单项属于它；外部不能直接改订单项，必须通过订单方法
class Order {
    private OrderId id;
    private List<OrderLine> lines;
    private Money total;

    void addLine(Product p, int qty) {
        lines.add(new OrderLine(p, qty));
        total = total.add(p.price().multiply(qty)); // 保持总额不变量
    }
}
```

通过 `addLine` 而非直接操作 `lines`，保证「总额 = 各项之和」这一业务不变量永不被破坏。

### 示例 2：领域事件解耦

```python
@dataclass
class OrderPlaced(DomainEvent):
    order_id: str
    amount: Decimal

# 下单成功后发布事件，邮件/库存/风控各自订阅，下单逻辑本身不依赖它们
event_bus.publish(OrderPlaced(order.id, order.total))
```

下单核心逻辑保持纯净，副作用通过事件异步传播。

### 示例 3：限界上下文与微服务边界

电商系统中「订单上下文」与「库存上下文」是不同限界上下文：订单关心履约，库存关心可用量。二者通过防腐层（ACL）转换模型，避免一个上下文的概念污染另一个——这往往就是微服务拆分的天然边界。

## 易错点

- **把 DDD 当 CRUD 框架**：DDD 不是技术框架，而是建模思想；小项目强行全套 DDD 反而过度设计。
- **聚合划分过大/过小**：过大则事务与锁范围太宽、性能差；过小则跨聚合的不变量无法保证（应改用最终一致性 + 领域事件）。
- **滥用实体、忽视值对象**：能用值对象（不可变、按属性相等）就别用实体，可减少大量身份管理与并发麻烦。
- **通用语言只停留在文档**：若代码命名与讨论术语不一致，通用语言就失效了——必须落到类名/方法名。
- **跨聚合直接引用**：聚合之间应只持有对方标识（ID），而非对象引用，以保持边界与独立事务。

## 练习

1. 给定「电商下单」场景，划分实体、值对象与聚合根，并说明一致性边界在哪。
2. 为什么「账户」在支付与社交中应是不同限界上下文？如何防止概念串味？
3. 用一句话说明领域事件解决了什么耦合问题。

## 小结

DDD 把「业务复杂度」放在软件设计的核心：战略上以通用语言和限界上下文切分自洽模型，战术上用实体、值对象、聚合、领域事件与仓储把规则固化进代码。它与微服务、CQRS、事件溯源天然契合，是构建可理解、可演化的复杂业务系统的关键方法论——但也要避免在小项目上过度设计。
