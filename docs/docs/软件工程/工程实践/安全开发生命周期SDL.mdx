## 核心概念

### 什么是 SDL，为什么需要它

传统做法把安全留到测试或上线前，导致漏洞修复成本极高（越晚发现越贵）。**SDL** 由微软提出，主张把安全要求**嵌入软件生命周期的每个阶段**：需求、设计、实现、验证、发布、响应。核心理念是「**安全左移（shift left）**」——问题越早发现、修复越便宜。

### SDL 的阶段与实践

1. **安全培训**：开发与安全人员建立共同基线（OWASP Top 10、常见漏洞类型）。
2. **安全要求**：在需求阶段明确安全与隐私需求、合规约束（如 GDPR、等保）。
3. **安全设计**：做**威胁建模**，定义攻击面，选择缓解措施。
4. **安全实现**：使用安全编码规范、禁用危险 API、依赖管理。
5. **安全验证**：静态/动态分析、模糊测试、渗透测试。
6. **发布**：对产物签名、建立漏洞响应机制。
7. **响应**：事故预案、补丁流程、复盘。

### 威胁建模：STRIDE

STRIDE 是经典的威胁分类框架，针对每个组件/数据流问六类问题：

| 字母 | 威胁 | 对应安全属性 | 典型缓解 |
|------|------|------|------|
| **S**poofing | 伪装身份 | 认证 | 强认证、签名 |
| **T**ampering | 篡改数据 | 完整性 | 校验和、HMAC、签名 |
| **R**epudiation | 抵赖 | 不可否认 | 审计日志 |
| **I**nformation disclosure | 信息泄露 | 机密性 | 加密、最小权限 |
| **D**enial of service | 拒绝服务 | 可用性 | 限流、冗余 |
| **E**levation of privilege | 提权 | 授权 | 最小权限、沙箱 |

常用工具是 **数据流图（DFD）**：画出处理、数据流、存储、外部实体，逐节点用 STRIDE 拷问。还有 **攻击树**、**PASTA** 等更重的方法论。

### 自动化检测手段

- **SAST（静态应用安全测试）**：不运行代码，扫描源码/字节码找危险模式（SQL 注入、硬编码密钥）。误报多但能早发现问题，适合接 CI。
- **DAST（动态应用安全测试）**：在运行态对暴露的接口发起攻击式探测，发现运行时漏洞。
- **SCA（软件成分分析）**：清点第三方依赖，对照漏洞库（CVE）报告已知风险——应对「供应链攻击」的关键。
- **IAST / 模糊测试（Fuzzing）**：向输入灌入海量畸形数据，观察是否崩溃或异常，擅长发现内存破坏与解析漏洞。

### 供应链与密钥安全

- **供应链安全**：依赖项可能被投毒（如恶意 npm 包）。对策：锁文件、私有源、SCA 扫描、签名验证、最小依赖。
- **密钥管理**：严禁把密钥/令牌硬编码进代码或提交仓库（[之前的明文 PAT 泄露](/docs/人工智能/大模型与应用/AI安全对齐) 就是教训）。用密钥管理服务（Vault/KMS/云 Secret）、环境变量、短期凭证。
- **最小权限与纵深防御**：每个组件只拥有必要权限，多层防线使单点失守不至于全线崩溃。

### 本章主线

SDL 的本质是「安全左移、内建而非外挂」：用威胁建模在设计阶段就预见攻击，用 SAST/DAST/SCA/Fuzzing 在验证阶段自动捕获，用供应链与密钥管理堵住最常见的失守点。它把安全从「事后救火」变成「全程工程纪律」。

## 示例

### 示例 1：用 STRIDE 拷问一个登录接口

- **S**：能否伪造他人身份？→ 强制多因素、防重放。
- **T**：令牌能否被篡改？→ 用签名 JWT，服务端校验。
- **R**：用户能否抵赖操作？→ 记录带身份审计日志。
- **I**：密码/会话是否泄露？→ 传输 TLS、存储加盐哈希、HttpOnly Cookie。
- **D**：能否被刷爆？→ 登录限流、验证码。
- **E**：能否越权访问他人数据？→ 服务端按身份校验资源归属（防 IDOR）。

### 示例 2：把 SAST 接进 CI

```yaml
# .github/workflows/security.yml（示意）
security-scan:
  steps:
    - uses: actions/checkout@v4
    - run: npm audit --audit-level=high      # 依赖漏洞（SCA）
    - run: semgrep --config auto              # 静态规则扫描（SAST）
    - run: trufflehog filesystem ./ --only-verified  # 扫硬编码密钥
```

任何高危命中即中断合并，把漏洞挡在合入前。

### 示例 3：绝不硬编码密钥

```python
# 错误：密钥进了代码仓库，一旦泄露全盘皆输
API_KEY = "sk_live_3f9a..."   # 灾难

# 正确：从环境变量/密钥管理服务读取，且用短期凭证
import os
API_KEY = os.environ["API_KEY"]   # 运行时注入，不进版本控制
```

## 易错点

- **把安全当上线前一步**：等测试阶段才发现设计级漏洞，返工成本极高；安全必须左移进需求与设计。
- **威胁建模走过场**：只画 DFD 不复盘 STRIDE 六类，等于没做；要逐节点「拷问」。
- **只靠 SAST 不修误报**：SAST 误报多，若不调优会被开发者无视；应结合规则裁剪与人工研判。
- **忽视供应链**：自写代码再安全，一个被投毒的依赖就能攻破；SCA 与锁文件不可省。
- **密钥进仓库**：硬编码凭证是最常见、最致命的失误，务必用环境变量/密钥管理服务 + 短期凭证。

## 小结

SDL 把安全从「事后救火」转变为「全程内建」：在需求与设计阶段用威胁建模（STRIDE/DFD）预见攻击，在实现与验证阶段用 SAST/DAST/SCA/模糊测试自动捕获漏洞，在发布与响应阶段用签名、补丁与复盘闭环。供应链安全与密钥管理堵住最常见的失守点。它是现代研发不可或缺的「安全工程纪律」，尤其在与 [可观测性](/docs/软件工程/工程实践/可观测性) 联动后能形成「发现-防护-响应」的完整闭环。
