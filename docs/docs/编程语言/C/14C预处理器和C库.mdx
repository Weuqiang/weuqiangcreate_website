## 核心概念

预处理在编译之前「纯文本」地改写源码：`#include` 把头文件贴进来，`#define` 做字符串替换，条件编译按宏决定哪些代码参与编译。宏不是函数——它不做类型检查、可能产生多次求值副作用。

本章主线：
- 预处理三件套：`#include`/`#define`/条件编译
- 带参宏 vs 函数：替换语义与括号
- 宏的常见坑（多次求值、优先级）
- 标准库头文件组织

## 条件编译

- 在很多情况下，我们希望程序的其中一部分代码只有在满足一定条件时才进行编译，否则不参与编译(只有参与编译的代码最终才能被执行)，这就是条件编译。
- 为什么要使用条件编译
  - 1)按不同的条件去编译不同的程序部分,因而产生不同的目标代码文件。有利于程序的移植和调试。
  - 2)条件编译当然也可以用条件语句来实现。 但是用条件语句将会对整个源程序进行编译,生成 的目标代码程序很长,而采用条件编译,则根据条件只编译其中的程序段 1 或程序段 2,生成的目 标程序较短。
    ##if-#else 条件编译指令
- 第一种格式:
  - 它的功能是,如常量表达式的值为真(非 0),则将 code1 编译到程序中,否则对 code2 编译到程序中。
  - 注意:
  - 是将代码编译进可执行程序, 而不是执行代码
  - 条件编译后面的条件表达式中不能识别变量,它里面只能识别常量和宏定义

```c showLineNumbers
#if 常量表达式
    ..code1...
#else
    ..code2...
#endif
```

```c showLineNumbers
#define SCORE 67
#if SCORE > 90
    printf("优秀\n");
#else
    printf("不及格\n");
#endif
```

- 第二种格式:

```c showLineNumbers
#if 条件1
  ...code1...
 #elif 条件2
  ...code2...
 #else
  ...code3...
 #endif
```

```c showLineNumbers
#define SCORE 67
#if SCORE > 90
    printf("优秀\n");
#elif SCORE > 60
    printf("良好\n");
#else
    printf("不及格\n");
#endif
```


## 模块化编程基础

### 为什么需要模块化编程？

随着程序规模的增长，将所有代码写在一个文件中会导致：
- 代码难以维护
- 功能耦合严重
- 团队协作困难
- 代码复用性差

模块化编程通过将功能拆分到不同的文件中，提高了代码的：
- **可维护性** - 每个模块职责单一
- **可复用性** - 模块可以在多个项目中使用
- **可测试性** - 独立模块更容易测试

## 头文件和源文件分离

### 基本概念

- **头文件（.h）**：包含函数声明、类型定义、宏定义等
- **源文件（.c）**：包含函数的具体实现

### 示例：数学工具模块

#### 1. 创建头文件 `math_utils.h`

```c showLineNumbers
#ifndef MATH_UTILS_H  // 防止重复包含
#define MATH_UTILS_H

// 函数声明
int add(int a, int b);
int subtract(int a, int b);
int multiply(int a, int b);
double divide(double a, double b);

// 常量定义
#define PI 3.14159265359

// 结构体定义
typedef struct {
    double x;
    double y;
} Point;

// 函数声明
double point_distance(const Point* p1, const Point* p2);

#endif // MATH_UTILS_H
```

#### 2. 创建源文件 `math_utils.c`

```c showLineNumbers
#include <math.h>
#include "math_utils.h"

int add(int a, int b) {
    return a + b;
}

int subtract(int a, int b) {
    return a - b;
}

int multiply(int a, int b) {
    return a * b;
}

double divide(double a, double b) {
    if (b != 0) {
        return a / b;
    }
    return 0.0; // 简单的错误处理
}

double point_distance(const Point* p1, const Point* p2) {
    double dx = p1->x - p2->x;
    double dy = p1->y - p2->y;
    return sqrt(dx * dx + dy * dy);
}
```

#### 3. 使用模块 `main.c`

```c showLineNumbers
#include <stdio.h>
#include "math_utils.h"

int main() {
    // 使用基本数学函数
    int result = add(10, 5);
    printf("10 + 5 = %d\n", result);
    
    // 使用结构体和函数
    Point p1 = {0, 0};
    Point p2 = {3, 4};
    double distance = point_distance(&p1, &p2);
    printf("Distance: %.2f\n", distance);
    
    // 使用常量
    printf("PI = %.5f\n", PI);
    
    return 0;
}
```

#### 4. 编译和链接

```bash
# 编译所有源文件
gcc -c math_utils.c -o math_utils.o
gcc -c main.c -o main.o

# 链接生成可执行文件
gcc math_utils.o main.o -lm -o calculator

# 或者一步完成
gcc main.c math_utils.c -lm -o calculator
```

### 使用Makefile管理编译

```makefile
# Makefile示例
CC = gcc
CFLAGS = -Wall -Wextra -Iinclude
SRCDIR = src
OBJDIR = build
TARGET = myapp

# 查找所有.c文件
SOURCES = $(wildcard $(SRCDIR)/*.c $(SRCDIR)/*/*.c)
OBJECTS = $(SOURCES:$(SRCDIR)/%.c=$(OBJDIR)/%.o)

.PHONY: all clean

all: $(TARGET)

$(TARGET): $(OBJECTS)
	$(CC) $(OBJECTS) -o $@

$(OBJDIR)/%.o: $(SRCDIR)/%.c
	@mkdir -p $(dir $@)
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -rf $(OBJDIR) $(TARGET)

install: $(TARGET)
	cp $(TARGET) /usr/local/bin/

.PHONY: help
help:
	@echo "Available targets:"
	@echo "  all     - Build the application"
	@echo "  clean   - Remove build files"
	@echo "  install - Install to system"
	@echo "  help    - Show this help"
```

### 2. 手动安装第三方库

以安装cJSON库为例：

```bash

git clone https://github.com/DaveGamble/cJSON.git
cd cJSON

# 编译和安装
mkdir build
cd build
cmake ..
make
sudo make install
```

### 3. 使用第三方库示例

```c showLineNumbers
#include <stdio.h>
#include <cjson/cJSON.h>

int main() {
    // 创建JSON对象
    cJSON *json = cJSON_CreateObject();
    cJSON *name = cJSON_CreateString("张三");
    cJSON *age = cJSON_CreateNumber(25);
    cJSON *skills = cJSON_CreateArray();
    
    // 添加技能数组
    cJSON_AddItemToArray(skills, cJSON_CreateString("C"));
    cJSON_AddItemToArray(skills, cJSON_CreateString("Python"));
    
    // 组装JSON对象
    cJSON_AddItemToObject(json, "name", name);
    cJSON_AddItemToObject(json, "age", age);
    cJSON_AddItemToObject(json, "skills", skills);
    
    // 输出JSON字符串
    char *json_string = cJSON_Print(json);
    printf("JSON: %s\n", json_string);
    
    // 解析JSON字符串
    cJSON *parsed = cJSON_Parse(json_string);
    if (parsed != NULL) {
        cJSON *name_item = cJSON_GetObjectItem(parsed, "name");
        if (cJSON_IsString(name_item)) {
            printf("Name: %s\n", name_item->valuestring);
        }
    }
    
    // 清理内存
    free(json_string);
    cJSON_Delete(json);
    cJSON_Delete(parsed);
    
    return 0;
}
```

编译命令：
```bash
gcc main.c -lcjson -o json_demo
```

## 创建静态库和动态库

### 静态库（.a文件）

```bash
# 编译目标文件
gcc -c math_utils.c -o math_utils.o
gcc -c string_utils.c -o string_utils.o

# 创建静态库
ar rcs libmyutils.a math_utils.o string_utils.o

# 使用静态库
gcc main.c -L. -lmyutils -o myapp
```

### 动态库（.so文件）

```bash
# 编译位置无关代码
gcc -c -fPIC math_utils.c -o math_utils.o
gcc -c -fPIC string_utils.c -o string_utils.o

# 创建动态库
gcc -shared -o libmyutils.so math_utils.o string_utils.o

# 使用动态库
gcc main.c -L. -lmyutils -o myapp

# 运行时需要设置库路径
export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH
./myapp
```

## CMake构建系统

手写 `gcc` 命令或维护 Makefile，在跨平台、多目录、多依赖的项目里很快会失控：Windows 上要用 MSVC，Linux/macOS 上要用 gcc/clang，编译参数与链接库各不相同。CMake 是一个**元构建系统**（build generator）：它本身不直接编译代码，而是根据一份平台无关的 `CMakeLists.txt` 生成 Visual Studio、Makefile、Ninja 等原生构建文件，再由原生工具去真正编译。

最小可运行的 `CMakeLists.txt` 只需三行：指定最低版本、声明项目名、登记要编译的可执行文件。

```cmake
cmake_minimum_required(VERSION 3.10)
project(hello)

add_executable(hello main.c)
```

把 `add_executable(hello main.c)` 换成 `add_library(math_utils math_utils.c)` 即改为生成库；再用 `target_link_libraries(hello math_utils)` 把库链接进可执行文件。常用指令分工如下：

- `add_executable(<目标名> 源文件...)`：登记一个可执行文件目标。
- `add_library(<库名> 源文件...)`：登记一个库目标（默认静态库，加 `SHARED` 关键字生成动态库）。
- `target_link_libraries(<目标> 库...)`：把库链接到某目标，自动处理链接顺序与传递依赖。
- `include_directories(<目录>...)`：为目标添加头文件搜索路径（现代写法更推荐用 `target_include_directories(<目标> PRIVATE <目录>)` 精确控制作用域）。

CMake 强烈推荐 **out-of-source（源外）构建**，即编译产物不污染源码目录。标准三步命令如下：

```bash
cmake -B build      # 在 build/ 目录生成原生构建文件（-B 指定构建目录）
cmake --build build # 调用原生工具真正编译
./build/hello       # 运行产物
```

多目录项目通常用「顶层 + 子目录」组织：顶层 `CMakeLists.txt` 用 `add_subdirectory(src)` 把子目录纳入构建，子目录里再各自写一份 `CMakeLists.txt` 用 `add_library` / `add_executable` 登记自己的目标，目录之间通过 `target_link_libraries` 和 `target_include_directories` 建立依赖。这样每个模块只关心自己的源文件，扩展新功能时只需新增子目录并在顶层登记，避免了巨型单文件的维护噩梦。

## 单元测试

单元测试的目标是**用代码验证每个函数的最小行为**：给定已知输入，断言得到预期输出。C 语言没有内置测试框架，做法分两派。

轻量方案直接复用标准库 `<assert.h>` 的 `assert()` 宏：条件为假时打印错误并 `abort()`。适合快速验证、零依赖，但缺点明显——所有用例写在一个 `main` 里、失败即整体中止、无法统计通过率、不支持 mock。

```c showLineNumbers
#include <assert.h>

int add(int a, int b) { return a + b; }

int main(void) {
    assert(add(2, 3) == 5);   // 断言不成立，程序直接中止
    assert(add(-1, 1) == 0);
    return 0;
}
```

当项目变大、需要分组与统计时，应引入真正的测试框架：

- **Unity**：纯 C 写成、单头文件即可引入，极致轻量，常用于嵌入式。
- **CMocka**：支持 mock 函数、可独立运行每个用例，适合需要打桩的中大型项目。
- **Check**：较早的框架，提供测试套件与 fork 隔离，但依赖相对重。

取舍原则：嵌入式或快速验证选 Unity；需要 mock 外部依赖（如硬件、网络）选 CMocka；想要成熟套件机制且能接受额外依赖可选 Check。

将测试接入 CMake 的标准做法是启用 CTest：在 `CMakeLists.txt` 里 `enable_testing()`，再为每个测试可执行文件登记 `add_test(NAME <名字> COMMAND <可执行文件>)`。

```cmake
enable_testing()
add_executable(test_math test_math.c math_utils.c)
add_test(NAME test_add COMMAND test_math)
```

之后用 `cmake -B build && cmake --build build && ctest --test-dir build` 即可一键跑全部测试，`ctest` 会汇总每个用例的通过与失败。

## 易错点

- 宏参数不加括号：`#define SQUARE(x) x*x` 遇到 `SQUARE(a+b)` 展开成 `a+b*a+b`，结果全错；正确写法是 `#define SQUARE(x) ((x)*(x))`，每个参数和整体都要括起来。
- 宏的多次求值副作用：`#define MAX(a,b) ((a)>(b)?(a):(b))` 在 `MAX(i++, j++)` 时会让参数自增两次，带副作用的表达式绝不要传进宏。
- 宏定义末尾误加分号：`#define N 10;` 会让 `int a[N];` 展开成 `int a[10;];`，编译报错的位置和提示都极具迷惑性。
- 多语句宏不用 `do { ... } while (0)` 包裹：跟在没写花括号的 `if` 后面时，只有第一条语句受条件控制，其余语句无条件执行。
- 头文件漏写包含守卫（`#ifndef` 加 `#define` 加 `#endif`，或 `#pragma once`）：被间接包含两次就会报类型或变量重复定义。
- 用 `#if MACRO` 判断一个可能未定义的宏：未定义的标识符会被当作 0 参与运算且不报错，宏名拼错时分支会静默走反；判断是否定义应当用 `#ifdef` 或 `#if defined(MACRO)`。
