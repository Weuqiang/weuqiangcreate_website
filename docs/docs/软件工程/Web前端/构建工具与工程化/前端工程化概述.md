# 前端工程化概述

- 知道 monorepo 解决什么协作问题

## 核心概念

工程化是把「个人能跑的小脚本」变成「团队可维护的产品」的一套纪律与工具链。它不写业务功能，却决定了功能能不能稳定、持续地交付。

本章主线：

- 工程化解决的三类问题
- 代码质量：lint 与 format
- 提交与集成门禁：git hooks + CI
- 仓库组织：monorepo

## 工程化解决什么

| 问题 | 表现 | 工程化手段 |
| --- | --- | --- |
| 不一致 | 每人代码风格不同、难以 review | ESLint + Prettier |
| 不可复现 | 本地能跑、CI 崩 | lockfile + CI 构建 |
| 易回归 | 改一处坏三处 | 测试 + 门禁 |
| 协作乱 | 多包版本对不上 | monorepo + 统一发布 |

## lint 与 format：职责不同

- **Lint（ESLint）**：查**逻辑与风险**——未定义变量、重复声明、`console.log` 残留、不安全的 `any`。可自动修复部分问题（`eslint --fix`）。
- **Format（Prettier）**：管**排版**——缩进、换行、引号、尾逗号。不问「对不对」，只问「好不好看」，且几乎不做语义判断。

两者常配合：Prettier 管格式、ESLint 关掉与它冲突的格式规则，只留逻辑检查。踩坑点：两者规则重叠会互相打架，需用 `eslint-config-prettier` 关掉 ESLint 的格式项。

## 提交门禁：git hooks 与 CI

```bash
# 用 husky 装 pre-commit hook（示意）
npx husky init
# .husky/pre-commit
npx lint-staged   # 只对暂存文件 lint + format
```

- **git hooks（如 husky + lint-staged）**：在提交前本地拦下明显问题，反馈快。
- **CI（GitHub Actions 等）**：在远端对每次推送/PR 跑 lint、测试、构建，**作为不可绕过的门禁**。本地 hook 可被 `--no-verify` 跳过，所以「真相之源」是 CI，不是本地 hook。

质量门禁的黄金法则：**能自动拦的，绝不靠人 review 拦**。

## monorepo：多包统一治理

当项目拆成多个互相依赖的包（如组件库 + 文档站 + 工具包），monorepo（用 pnpm workspace / Turborepo / Nx）让它们：

- 共享同一份依赖与配置
- 跨包改动能一次提交、一次验证
- 统一版本发布与构建缓存

代价是工具链复杂度上升。小项目单体仓库即可，不必为了「看起来专业」强上 monorepo。

## 易错点

1. **lint 当 format 用、反之亦然**：用 ESLint 管缩进会累且易冲突，交给 Prettier。
2. **只装本地 hook 不配 CI**：hook 可被跳过，质量门禁形同虚设。
3. **monorepo 过度设计**：单包项目硬拆多包，徒增构建与发布复杂度。
4. **pre-commit 跑全量检查**：慢到让人想跳过；用 lint-staged 只查改动文件。

## 小结

工程化是用工具链把「一致性、可复现、自动化」固化下来的过程：ESLint+Prettier 守格式与逻辑，husky+lint-staged 做本地快拦，CI 做不可绕过的远端门禁，monorepo 解决多包协作。它能让团队把精力花在功能上，而不是救火上。

## 练习

1. 在一个项目里同时接入 ESLint 与 Prettier，故意写一个格式混乱且有未定义变量的文件，观察两者分别报什么。
2. 配置一个 GitHub Actions，要求 PR 必须通过 `lint + test + build` 才允许合并。
3. 用 pnpm workspace 建两个互相依赖的包，体验跨包改动能一次验证。
