# 编译原理概览

`gcc hello.c -o hello` 这条命令背后发生了什么？源代码不是被「翻译」一次就变成可执行文件的，而是经过**预处理 → 编译 → 汇编 → 链接**四个独立阶段，每个阶段都产出一种中间产物。本篇把这条完整的流水线串起来，并补上前两篇未展开的**语义分析、目标代码生成、链接与运行时**三块。

## 学习目标

- 说出从源码到可执行文件的完整流水线，以及每个阶段的输入与输出。
- 区分编译器的**前端 / 中端 / 后端**，理解这种划分为何能让 $m$ 种语言 × $n$ 种硬件的组合从 $m \times n$ 降到 $m + n$。
- 说清编译型、解释型、JIT 三种执行模型的取舍。
- 亲手用 `gcc -E/-S/-c` 观察每一阶段的真实产物。

## 核心直觉

### 完整流水线

```text
hello.c
  │  ① 预处理 (cpp)      展开 #include / #define，删注释
  ▼
hello.i          纯 C 代码，无宏无头文件引用
  │  ② 编译 (cc1)        词法 → 语法 → 语义 → IR → 优化 → 目标代码
  ▼
hello.s          汇编代码（文本）
  │  ③ 汇编 (as)         汇编助记符 → 机器码
  ▼
hello.o          可重定位目标文件（二进制，符号未解析）
  │  ④ 链接 (ld)         合并 .o 与库，解析符号，重定位
  ▼
hello            可执行文件
  │  ⑤ 加载 (loader)     映射到虚拟地址空间，动态链接
  ▼
运行中的进程
```

其中第 ② 步「编译」内部又分六个子阶段，这才是狭义的「编译原理」：

| 子阶段 | 输入 | 输出 | 本站详解 |
|---|---|---|---|
| 词法分析 | 字符流 | Token 流 | [词法分析与语法分析](/docs/计算机科学基础/计算机科学导论/编译原理/词法与语法分析) |
| 语法分析 | Token 流 | 抽象语法树 AST | 同上 |
| 语义分析 | AST | 带类型标注的 AST + 符号表 | 本页 ↓ |
| 中间代码生成 | 标注 AST | IR（三地址码/SSA） | [中间代码与优化](/docs/计算机科学基础/计算机科学导论/编译原理/中间代码与优化) |
| 优化 | IR | 更优的 IR | 同上 |
| 目标代码生成 | IR | 汇编 | 本页 ↓ |

### 前端 / 中端 / 后端：编译器架构的核心决策

```text
   前端（与语言相关）        中端（与两者无关）      后端（与硬件相关）
  ┌──────────┐            ┌──────────┐          ┌──────────┐
  │ C   前端 │──┐         │          │      ┌──▶│ x86 后端 │
  │ C++ 前端 │──┼────────▶│  统一 IR  │──────┼──▶│ ARM 后端 │
  │ Rust 前端│──┤         │  + 优化   │      ├──▶│RISC-V后端│
  │ Swift前端│──┘         │          │      └──▶│WASM 后端 │
  └──────────┘            └──────────┘          └──────────┘
```

这是编译器工程最重要的架构决策。若前后端直接耦合，支持 $m$ 种语言和 $n$ 种硬件需要写 $m \times n$ 个编译器；引入统一 IR 后只需 $m + n$ 个模块。

LLVM 正是这个思想的极致实践：Clang（C/C++）、rustc、Swift 都把代码降低到 **LLVM IR**，然后共享同一套优化器和所有后端。这就是为什么 Rust 一诞生就能支持几十种平台——它不需要自己写后端。

### 语义分析：语法对了不代表有意义

语法分析只检查「形式是否合规」，语义分析检查「意思是否讲得通」。经典对比：

```c
int x = "hello";     // 语法完全合法，语义错误：类型不匹配
undefined_var + 1;   // 语法合法，语义错误：变量未声明
```

语义分析的三项核心工作：

**1. 符号表管理**。符号表记录每个标识符的类型、作用域、存储位置。它通常实现为**作用域栈**——进入块时压入新的哈希表，退出时弹出：

```c
int x = 1;          // 全局作用域：x → int
void f() {
    int x = 2;      // 函数作用域：x → int（遮蔽全局的 x）
    {
        float x = 3.0;  // 块作用域：x → float（再次遮蔽）
    }                   // 退出块，弹出该层，x 恢复为 int
}
```

查找标识符时从栈顶向下逐层搜索，找到的第一个就是有效声明——这就是「变量遮蔽（shadowing）」的实现原理。

**2. 类型检查**。验证运算符与操作数类型兼容、函数调用的实参与形参匹配、返回值类型正确。静态类型语言在此报错；动态类型语言把这些检查推迟到运行时。

**3. 其他静态检查**：变量使用前是否已声明、`break`/`continue` 是否在循环内、函数是否所有路径都有返回值、常量是否被修改。

### 目标代码生成：三个经典难题

从 IR 到汇编要解决三件事：

| 难题 | 说明 | 常用算法 |
|---|---|---|
| **指令选择** | 一个 IR 操作可能对应多种指令组合，选哪种？ | 树覆盖、动态规划 |
| **寄存器分配** | 寄存器只有十几个，变量可能上百个，谁进寄存器？ | **图着色**、线性扫描 |
| **指令调度** | 重排指令顺序以填充流水线空隙、隐藏访存延迟 | 列表调度 |

**寄存器分配是其中最经典的**：把「同时活跃的变量不能共用寄存器」建模成图着色问题——变量是顶点，同时活跃的两个变量之间连边，可用寄存器数就是颜色数。图着色是 NP 完全问题，所以实际编译器用启发式算法。分配不下的变量会被**溢出（spill）** 到栈上，每次访问都要多一次内存读写——这也是为什么手写循环里变量太多会变慢。

### 三种执行模型

| 模型 | 代表 | 何时翻译 | 启动速度 | 运行速度 | 跨平台 |
|---|---|---|---|---|---|
| **编译型** | C、C++、Rust、Go | 运行前一次性 | 最快 | 最快 | 需为每平台重新编译 |
| **解释型** | Python、Ruby、Shell | 运行时逐句 | 快 | 慢（10～100 倍） | 好 |
| **字节码 + VM** | Java、C#、Python(.pyc) | 编译成字节码，VM 解释 | 中 | 中 | 很好 |
| **JIT** | JVM HotSpot、V8、PyPy | 运行时把热点编译成机器码 | 慢（预热） | 接近编译型，有时更快 | 好 |
| **AOT** | GraalVM Native Image、Dart | 提前编译成原生码 | 最快 | 快 | 需重新编译 |

**JIT 为什么有时比静态编译还快？** 因为它掌握**运行时信息**：知道哪个分支实际常走、知道虚函数的实际类型、知道循环的真实迭代次数。基于这些「画像」，它能做静态编译器做不到的激进优化（如内联虚调用、去虚拟化）。代价是预热时间和内存占用。

## 最小示例

### 亲手观察四个阶段

```bash
# 准备一个最小源文件
cat > hello.c <<'EOF'
#include <stdio.h>
#define TIMES 3

int add(int a, int b) {
    return a + b;
}

int main(void) {
    for (int i = 0; i < TIMES; i++) {
        printf("%d\n", add(i, 10));
    }
    return 0;
}
EOF

# ① 预处理：宏展开、头文件插入
gcc -E hello.c -o hello.i
wc -l hello.c hello.i      # 13 行 → 700+ 行（stdio.h 被整个插进来了）
grep -n "TIMES" hello.i    # 无结果：宏已被替换成字面量 3

# ② 编译成汇编
gcc -S -O0 hello.c -o hello.s
grep -A6 "^add:" hello.s   # 看 add 函数的汇编

# ③ 汇编成目标文件
gcc -c hello.s -o hello.o
nm hello.o                 # 查看符号表
#   0000000000000000 T add      ← T = 本文件定义的全局符号
#                    U printf   ← U = 未定义，等待链接器解析

# ④ 链接成可执行文件
gcc hello.o -o hello
nm hello | grep printf     # printf 已被解析
ldd hello                  # 查看依赖的动态库（libc.so.6）
./hello                    # 10 11 12
```

`nm` 输出里的 **U（Undefined）** 最能说明链接器的作用：`hello.o` 里 `printf` 只是一个待填的空洞，链接器负责把它绑定到 C 标准库中的真实地址。这也解释了那个最常见的错误——「undefined reference to ...」意味着链接阶段没找到某个符号的定义，通常是漏了 `-l` 库参数或忘了实现函数。

### 优化的直观效果

```bash
gcc -O0 -S hello.c -o O0.s
gcc -O2 -S hello.c -o O2.s
wc -l O0.s O2.s
```

在 `-O2` 下，编译器通常会：把 `add(i, 10)` **内联**成 `i + 10`、把循环**展开**成三次直接调用、把 `i < 3` 的循环边界**常量传播**掉。汇编行数往往显著减少，而 `add` 函数可能整个消失（被内联后无人调用）。

### 语义分析实战：一个迷你符号表

用 Python 模拟作用域栈与类型检查：

```python
class SymbolTable:
    def __init__(self):
        self.scopes = [{}]                       # 作用域栈，栈底是全局

    def enter_scope(self):
        self.scopes.append({})

    def exit_scope(self):
        self.scopes.pop()

    def declare(self, name, typ):
        if name in self.scopes[-1]:              # 只查当前层：允许遮蔽，禁止重复声明
            raise SyntaxError(f"重复声明: {name}")
        self.scopes[-1][name] = typ

    def lookup(self, name):
        for scope in reversed(self.scopes):      # 从内层往外找
            if name in scope:
                return scope[name]
        raise NameError(f"未声明的标识符: {name}")


def type_check(op, left, right):
    """极简类型规则：int 可隐式提升为 float，其余不兼容"""
    numeric = {"int", "float"}
    if left in numeric and right in numeric:
        return "float" if "float" in (left, right) else "int"
    if left == right == "str" and op == "+":
        return "str"
    raise TypeError(f"类型不兼容: {left} {op} {right}")


st = SymbolTable()
st.declare("x", "int")
st.declare("msg", "str")

st.enter_scope()
st.declare("x", "float")                          # 内层遮蔽外层
print("内层 x 的类型:", st.lookup("x"))            # float
print("内层看 msg:", st.lookup("msg"))             # str（外层可见）
st.exit_scope()

print("外层 x 的类型:", st.lookup("x"))            # int（恢复）

print("int + float =", type_check("+", "int", "float"))   # float
try:
    type_check("+", "int", "str")
except TypeError as e:
    print("捕获:", e)                              # 类型不兼容: int + str
try:
    st.lookup("undefined_var")
except NameError as e:
    print("捕获:", e)                              # 未声明的标识符: undefined_var
```

**手动推演作用域栈的变化**：

| 步骤 | 作用域栈 | `lookup("x")` 结果 |
|---|---|---|
| 声明全局 x:int | `[{x:int, msg:str}]` | int |
| enter_scope | `[{x:int, msg:str}, {}]` | int（外层可见） |
| 声明内层 x:float | `[{x:int, msg:str}, {x:float}]` | **float**（遮蔽） |
| exit_scope | `[{x:int, msg:str}]` | int（恢复） |

这个「从栈顶向下查找」的规则，就是所有块作用域语言（C、Java、Rust、JavaScript 的 `let`）变量遮蔽行为的统一解释。

## 易错点

1. **把「编译」和「链接」的错误搞混。** 编译错误是语法或类型问题（`error: expected ';'`、`incompatible types`），链接错误是符号找不到（`undefined reference to 'foo'`）。前者改代码，后者通常是漏了库或漏了实现。看错误信息属于哪一阶段，能省一半排查时间。

2. **以为解释型语言不编译。** Python 也会先编译成字节码（`.pyc`），只是由虚拟机解释执行而非直接跑在 CPU 上。「编译 vs 解释」是**执行策略**的区别，不是「有没有翻译」的区别。

3. **混淆「语言」与「实现」。** C 也可以有解释器（如 Cling），Python 也可以被编译成原生码（Nuitka、Cython）。**编译型/解释型是实现的属性，不是语言的属性。**

4. **过度依赖 `-O3`。** 更激进的优化可能改变浮点运算顺序导致精度差异，也可能因代码膨胀降低指令缓存命中率而变慢。生产环境通常用 `-O2`，且要实测。

5. **忽视未定义行为（UB）给优化带来的后果。** C/C++ 里的有符号整数溢出、空指针解引用、越界访问都是 UB。编译器**假定 UB 不会发生**并据此优化，于是可能直接删掉你的检查代码。这类 bug 只在开优化后出现，极难调试。

6. **误以为静态链接总是更好。** 静态链接产物体积大、库有安全更新时必须重新编译整个程序；动态链接省空间、便于统一升级，但有「DLL 地狱」的版本兼容问题。容器化时代静态链接（如 Go 的默认行为）重新流行，因为它简化了部署。

7. **忘了 `#include` 是纯文本插入。** 预处理不理解 C 语法，`#include` 就是把文件内容原样贴进来。这解释了为什么需要头文件保护（`#pragma once` 或 `#ifndef` 宏），否则重复包含会导致重复定义。

## 练习

1. 按「最小示例」跑完四个阶段，回答：`hello.i` 有多少行？`hello.o` 的 `nm` 输出里有几个 `U` 符号？它们分别在链接后指向哪里？
2. 写一个含未定义函数 `int mystery(int);` 但只声明不实现的程序，观察它能通过 `gcc -c` 却在链接时报错。这印证了编译与链接是独立阶段。
3. 用 `gcc -O0 -S` 和 `gcc -O2 -S` 对比同一个含简单循环的函数，找出编译器做了哪些优化（提示：找找循环还在不在、`add` 函数有没有被内联）。
4. 扩展上面的 `SymbolTable`，加入函数符号（记录参数类型列表与返回类型），并实现「函数调用时检查实参个数与类型」。
5. 用 Python 的 `dis` 模块查看一个函数的字节码：`import dis; dis.dis(lambda x: x * 2 + 1)`。对照 C 的汇编，体会「字节码」与「机器码」的抽象层次差异。
6. 查阅 LLVM IR 的语法，用 `clang -S -emit-llvm hello.c -o hello.ll` 生成 IR 并阅读。找出其中的 SSA 特征（每个变量只被赋值一次）。
7. 解释为什么 Java 的「一次编译，到处运行」和 C 的「一次编写，到处编译」是两种不同的跨平台策略，各自的代价是什么。

## 小结

编译不是一次翻译，而是一条**层层降低抽象**的流水线：从人类可读的源码，到结构化的 AST，到与硬件无关的 IR，到特定架构的汇编，最后到二进制机器码。这条流水线上最有价值的架构思想是**前端/中端/后端的三段式解耦**——它把 $m \times n$ 的工程量压成 $m + n$，让 LLVM 成为现代语言生态的公共基础设施。理解这条流水线的实际收益很直接：你能一眼分清编译错误与链接错误、能读懂 `-O2` 到底做了什么、能明白为什么 UB 会让优化器「删掉你的代码」、也能理解 JIT 凭什么在某些场景下跑赢静态编译。
